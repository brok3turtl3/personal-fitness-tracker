## 1. System Classification

**System Type:** Hybrid — tool-using agentic conversational coach (single Claude model running a bounded multi-turn read-only tool loop)

**Description:**
A single-user, browser-only fitness coach. The user chats with Claude; Claude reads the user's *actual* logged data on demand through six read-only `query_*` tools (cardio, weight, readings, meals, daily totals, saved foods), runs an agentic loop (`while stop_reason === 'tool_use'`, bounded by `maxAgentTurns`), and answers with cross-domain insight grounded in the user's real logs. Every claim is annotated on two axes — confidence (`strong | moderate | weak | animal-only | anecdotal | speculative`) and source (`from your data` vs `from research`) — and the user can expand any message to inspect the underlying `tool_use`/`tool_result` blocks. "Good" = advice that is grounded in the user's real data, honestly graded for confidence and source, transparent about what was looked at, and never decorated with a fabricated clickable citation. This two-axis epistemic annotation is the product's deliberate replacement for clinical disclaimers.

**Critical Failure Modes:**
<!-- The 3-5 behaviors that absolutely cannot go wrong in this system -->
1. **A free-generated citation renders as a clickable link.** Only API-structured citation blocks (`web_search_result_location`, `search_result`) may ever become `<a href>`; any author-year / DOI / URL string the model writes freely in prose must render as plain text. (CHAT-09 / D-13 — the highest-stakes pitfall, fabricated citations at 14–95% rates, guarded at the rendering boundary one phase before web search exists.)
2. **An unfinished `tool_use` block wedges the loop.** The agentic loop must always terminate cleanly — on every terminal `stop_reason` (`end_turn`, `max_tokens`, refusal, `pause_turn`) and on the `maxAgentTurns` cap — never freeze, never spin past the cap, never block synchronously waiting on a write approval (D-03/D-04/D-16). A pending memory/profile write is fed a synthetic "surfaced for approval, not yet persisted" `tool_result` so the model can finish.
3. **A low-confidence or "from research" claim is presented as if it were strong / grounded in the user's data.** Confidence and source must be parsed faithfully; a `speculative` or `from research` claim must be visually unmistakable from a `from your data · strong` claim (color + icon + text, never color alone). A malformed/absent confidence token must degrade safely (claim renders unbadged — never crash, never fabricate a grade).
4. **The model mutates the user's data without approval, or a `query_*` tool dumps an unbounded dataset.** `query_*` tools are strictly read-only and auto-execute; any model-proposed write (memory/profile) re-validates through `validators.ts` (CHAT-11) and is never persisted without explicit user approval of the pending pill. Query output must be bounded/summarized to protect the token budget.
5. **The slim-context + cache contract silently breaks.** `messages.countTokens` (not `text.length/4`) must drive the rolling-window decision; the system-prompt prefix must stay stable so `cache_control: { type: 'ephemeral' }` yields ~10%-cost cache reads; `FitnessContextService` must emit a thin ~500-token header, not stuff the full dataset (CHAT-10 / D-15).

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Consumer health & fitness coaching / wellness — specifically AI-as-coach over a personal **Quantified-Self** health record (cardio, weight, blood pressure, blood glucose, ketones, diet & nutrition). The reference disciplines whose practitioners would actually grade this output are: (a) **registered dietitians / nutrition-science practitioners** (evidence-grading of dietary claims, the GRADE / Academy of Nutrition and Dietetics Evidence Analysis Library hierarchy, animal-vs-human evidence distinctions); (b) **certified fitness / strength coaches** (training-load and trend reasoning over a single client's logged data); (c) **health-literacy / evidence-communication practitioners** (calibrated hedging, honest uncertainty); and (d) the **diabetes / metabolic-health and ketogenic self-management community** (interpreting fasting glucose, glucose trends, and blood ketones — `mmol/L` — for personal n=1 metabolic experimentation). This is explicitly **NOT** clinical medicine, **NOT** a regulated medical device, **NOT** coach-to-client, and **NOT** a population deployment. It is a sophisticated adult coaching themselves with an AI over their own logs.

**User Population:** A single sophisticated user who is also the developer (`brok3turtl3@gmail.com`), running the app locally (browser / Electron renderer) with their own Anthropic API key. They author their own `UserProfile` (goals / preferences / dietary constraints / training history), log every cardio session / weight / BP / glucose / ketone reading / meal themselves, and chose this product *because* they want epistemic honesty (graded confidence + source attribution) over watered-down disclaimers. They are health-literate and self-experimenting — notably tracking blood glucose and ketones, which signals active metabolic-health / low-carb-or-keto self-management. There is no second user, no patient, no client, no shared deployment.

**Stakes Level:** **High (advice surface) / Low (deployment surface).** Phase 4 raises the advice surface from Phase 3's Medium to **High** for two structural reasons: (1) the agentic loop is now *live* — the coach actively reads real BP / glucose / ketone / weight / cardio / nutrition data and emits grounded coaching the user will act on, where Phase 3 was dormant plumbing; and (2) the two-axis annotation (confidence × source) is now the *only* thing standing between the model and an unhedged, unsourced health claim, because PROJECT.md deliberately removed clinical disclaimers. A confident dietary or training claim that affects someone managing blood sugar (e.g. a fasting-timing or carb-intake suggestion read against logged glucose) is the sharp edge. The deployment surface stays **Low**: one informed adult, own machine, own data, own key, no downstream users, no export, no automated decisions.

**Output Consequence:** What happens downstream when the AI output is acted on, in this app:
1. The user changes training intensity, diet, carb intake, fasting timing, or supplement use based on a coaching answer that the AI grounded in their actual logs (e.g. "your fasting glucose has trended up across your last 8 readings — `[evidence: moderate][source: data]`").
2. A `from research · {grade}` claim (Phase 4 = the model's own training knowledge, never a live source — D-12) shapes a belief the user carries forward: if `animal-only` mechanistic findings are framed as human-applicable, or a `speculative` claim is read as settled, the user may adopt a dietary/training change on weak footing.
3. The AI proposes a `UserProfile` edit or `memory` write via the pending pill (D-03); on approval, the AI's framing of a fact about the user ("you follow strict keto", "your goal is a sub-25 5K") becomes the prompt-context floor for every future turn — drift here compounds.
4. The user expands a `tool_use` disclosure (D-05/D-06) to verify *which* data produced a claim, or follows a data-claim→tool-call trace (D-11). If the disclosure misrepresents what was queried, the transparency promise — the product's core trust mechanism — is silently broken.

### Known Failure Modes in This Domain

How the generic risks manifest in *this* app's Phase-4 question surface — not generic hallucination:

1. **Confabulated own-data restatement under an agentic loop.** Now that the coach can call `query_*` tools, the dangerous case is a claim labeled `from your data · strong` whose number was *never returned by any tool* — the model inferred or rounded it. Worse than Phase 3's snapshot case, because the tool-use UI implies the number was actually read. Surfaces only if the user expands the disclosure or cross-checks `/readings`. (Sources: Pitfall 1; CHAT-08; QS data-integrity norm; D-11 traceability.)
2. **Mis-graded metabolic claims that bite a glucose/keto self-manager.** The user tracks blood glucose and ketones. A `from research` dietary claim graded too high — e.g. an animal-only mechanism about a fasting protocol presented as `strong` human guidance, or a single-study carb claim rendered `moderate` — can drive a real change in carb intake or fasting timing for someone managing blood sugar. The 6-level taxonomy is the safety mechanism; this failure mode is *that mechanism failing*. (Sources: Academy of Nutrition & Dietetics / GRADE animal-vs-human evidence; PLOS One sports-nutrition-LLM weakness on nuanced areas; PMC AI-nutrition comparison.)
3. **Diagnosis drift past the no-clinical-guardrails contract.** Because the user explicitly declined disclaimers, the prompt has no "I am not a doctor" floor. An unhedged model can slide from "your fasting glucose is on the higher end — worth watching" to "you have prediabetes" in one turn, especially when glucose data is involved. Scope discipline + confidence grading are the only brakes. (Sources: PROJECT.md Key Decision + Out-of-Scope; arXiv 2507.21132; PMC lifestyle-medicine review.)
4. **Sycophantic confidence inflation.** The user asks a leading question ("my diet's working, right? my glucose looks better?") and the model agrees with inflated confidence rather than grading honestly against thin or contradictory logs — the documented dominant high-stakes LLM failure. Especially corrosive here because the whole product premise is calibrated honesty. (Source: arXiv 2507.21132.)
5. **Fabricated citation rendered as a live link.** The model, asked about research, writes a confident `Author et al., 2021` or a plausible DOI/URL in prose; if the renderer autolinks it, the user gets a clickable "source" for a study that does not exist — at the documented 14–95% fabrication rate. Phase 4 produces no real citations, so *anything* citation-shaped is fabricated, which is exactly why the guard ships now. (Sources: Pitfall 1; CoreProse / arXiv taxonomy; JMIR mental-health 19.9% fabrication.)
6. **Transparency theater — disclosure that doesn't match the data.** The live tool-call summary (D-01/D-05) says "Read 38 weight entries · Jan 1–May 31" but the result the model reasoned over was bounded/summarized differently (D-14), or the model narrates a query it didn't actually run. The user trusts the disclosure precisely because it's presented as an audit trail; a mismatch silently breaks the core trust mechanism. (Sources: CHAT-06; D-05/D-06; D-14 bounded output.)
7. **Memory entries that interpret rather than record (carried from Phase 3, now live).** With the loop active, the model can propose memory/profile writes mid-answer. "User is anxious about glucose" or "user struggles with adherence" persisted *as a fact* becomes the working assumption of every future turn and re-summarizes into something stronger. The pending-pill confirm-before-write (D-03) is the gate; the hygiene bar is facts-not-interpretations. (Sources: 03-AI-SPEC memory-hygiene dimension; Pitfall 9 memory drift; CHAT-04/D-03.)

### Regulatory / Compliance Context

**No regulatory compliance gate applies to this deployment context — and per PROJECT.md's Key Decision, none is to be bolted on.** The system is a personal tool used by one sophisticated adult on their own machine, holding their own health data and their own Anthropic API key, with no patient, client, employer relationship, third-party data subject, shared environment, or commercial distribution. HIPAA does not apply (the user is not a covered entity; no other person's PHI is processed). FDA Software-as-a-Medical-Device classification does not apply (no diagnostic, screening, or treatment claim is made — and the scope-discipline dimension above is precisely what keeps the coach on the **FDA "general wellness" / lifestyle side of the line**, away from device-like diagnostic claims). GDPR/CCPA do not apply (single data subject = the controller themselves).

The relevant norms are therefore **honesty conventions, not compliance gates** — and they map directly onto the product's chosen two-axis annotation rather than onto disclaimers:
- **FTC truth-in-health-claims norms** ("substantiate health claims; don't overstate evidence") are honored *by grading every claim's evidence strength and source* — the confidence taxonomy is the substantiation signal, surfaced to the user instead of hidden.
- **Dietary-supplement / structure-function claim conventions** ("describe how a nutrient affects body structure/function; don't claim to diagnose, treat, cure, or prevent disease") map onto the **scope-discipline** dimension (coaching, not diagnosis) — the coach can discuss how a dietary change relates to a logged trend, but must not name or claim to treat a disease.
- **FDA general-wellness vs medical-device line** is held by the same scope-discipline boundary: trend-watching and behavior suggestions are general-wellness; naming a condition or recommending a medication crosses toward device/clinical claims and is out of scope.

These are framed as **what keeps consumer health advice honest**, consistent with the deliberate no-clinical-disclaimer stance — not as features to implement. **If the project ever scaled** (multi-user, sync, export, public deployment, coach-to-client), the posture changes immediately: HIPAA-style handling for the BP/glucose/ketone surface, FTC enforcement exposure on any marketed health-outcome claim, and a fresh SaMD look for any diagnostic/medication feature. None of those triggers exist in Phase 4 or anywhere on the current roadmap.

## 2. Framework Decision

**Selected Framework:** `@anthropic-ai/sdk` — direct Anthropic TypeScript SDK, **no agent framework layered on**

**Version:** `^0.92.0` (already adopted in Phase 3; pin the existing version from `package.json`)

**Rationale:**
Every agent framework in the decision matrix is eliminated by a hard constraint. TypeScript-only kills the Python ecosystem (CrewAI, AG2/AutoGen, Haystack, Google ADK). Browser-only + no-backend kills LangGraph, whose entire value is server-side checkpointing/persistence (Postgres/Redis) — unusable and pointless in a browser sandbox. The project's explicit "tool calls over typed services beat RAG" decision (REQUIREMENTS.md, no vector DB/embeddings) plus single-user simplicity rules out LlamaIndex and LangChain (and "LangChain for a simple chatbot" is a documented anti-pattern). The Phase 4 agentic loop is a thin `while (stop_reason === 'tool_use')` (~30 lines) over typed SDK surfaces the codebase already reaches (`tools[]`, `cache_control`, `messages.countTokens`), dispatching through the Phase 3 `ToolRegistryService`. Adopting any framework would discard working Phase 3 plumbing (`ToolRegistryService`, `chat-block-serializer`, `ChatBlock` union, V5 schema) and add an unusable abstraction for zero gain. This is less "choosing a framework" than confirming the Phase 3 decision and declining to add an agent layer.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| Claude Agent SDK (TypeScript) | Only Anthropic-native TS framework, but its code/filesystem/shell/MCP primitives assume a Node runtime and are unusable in a browser. Revisit only if MCP servers or lifecycle hooks become a hard requirement. |
| LangGraph (TS) | Its raison d'être is server-side checkpointing/persistence; no backend exists and none is permitted (browser-only, LocalStorage). Graph overhead unjustified for a single linear tool loop. |
| LangChain (TS) | Abstraction overhead over a ~30-line loop; "LangChain for a simple chatbot" is a documented anti-pattern; model-agnostic value wasted under accepted Anthropic lock-in. |
| LlamaIndex (TS) | RAG/data framework; project explicitly chose tool calls over typed services instead of retrieval/embeddings. |
| CrewAI / AG2 / Haystack / Google ADK | Python (and Java) only — fail the TypeScript-only hard constraint outright. |
| OpenAI Agents SDK | OpenAI-optimized; Anthropic lock-in is the consciously accepted commitment. |

**Vendor Lock-In Accepted:** Yes — Anthropic/Claude-only, consciously accepted (locked in Phase 3). The system depends on Anthropic-specific surfaces (`stop_reason: 'tool_use'` loop shape, `cache_control: ephemeral`, `messages.countTokens`, structured citation blocks) that have no portable equivalent; portability was explicitly deprioritized in favor of integration depth and minimal diff over Phase 3.

```typescript
  StopReason,                 // 'end_turn' | 'max_tokens' | 'stop_sequence' | 'tool_use' | 'pause_turn' | 'refusal'
} from '@anthropic-ai/sdk/resources/messages';

// RxJS bridge — the only Promise→Observable seam. Phase 4 emits MANY turns, so the loop
// returns a multi-emit Observable<ChatTurnEvent> rather than a single Observable<Message>.
import { Observable, from } from 'rxjs';
```

> **Citation note (D-13):** the structured citation that may become a link lives on `TextBlock.citations` as a `TextCitation` whose `type` is `'search_result_location'` (RAG / `search_result` blocks) or `'web_search_result_location'` (Phase 5 web search). **In Phase 4 no tool produces either**, so `.citations` is always absent — but the renderer guard is built and adversarially tested now.

### Entry Point Pattern
```typescript
// services/chat.service.ts — the Phase 4 agentic loop. Replaces the Phase 3 single-shot send.
// Read-only query_* tools auto-execute (D-02); write proposals never block the loop (D-03);
// every terminal stop_reason is handled (D-16); the cap degrades gracefully (D-04).
//
// Returned as a multi-emit Observable so the UI can render live per-tool-call progress (D-01).
import { Observable } from 'rxjs';
import type {
  Message, MessageParam, ContentBlockParam, ToolResultBlockParam,
  ToolUseBlock, StopReason,
} from '@anthropic-ai/sdk/resources/messages';
import { toAnthropicContent, fromAnthropicMessage } from './chat-block-serializer';
import type { ChatBlock } from '../models/ai-chat.model';

type ChatTurnEvent =
  | { kind: 'tool_use_started'; block: ToolUseBlock }      // D-01 live progress
  | { kind: 'tool_result'; toolUseId: string; summary: string }
  | { kind: 'assistant_text'; blocks: ChatBlock[] }
  | { kind: 'turn_limit'; turnsUsed: number }              // D-04
  | { kind: 'done'; stopReason: StopReason };

runAgenticLoop(conversationId: string, apiKey: string): Observable<ChatTurnEvent> {
  return new Observable<ChatTurnEvent>((subscriber) => {
    let cancelled = false;

    (async () => {
      const maxAgentTurns = this.aiSettings.get().maxAgentTurns ?? 10;   // D-04 cap
      const model = this.aiSettings.get().selectedModel ?? CLAUDE_MODELS[0].value;
      const tools = this.toolRegistry.definitions();                     // query_* + memory defs
      const system = await this.fitnessContext.buildSystemPrompt();      // slim ~500-tok header + cache_control (D-15)

      // Sliding window built from persisted ChatBlock[] via the Phase 3 serializer.
      const messages: MessageParam[] = this.buildApiMessages(conversationId)
        .map((m) => ({ role: m.role, content: toAnthropicContent(m.blocks) }));

      for (let turn = 0; turn < maxAgentTurns && !cancelled; turn++) {
        let response: Message;
        try {
          response = await this.anthropicApi.send(apiKey, {
            model,
            max_tokens: this.aiSettings.get().maxResponseTokens ?? 4096, // ALWAYS explicit (4b.3)
            system,                                                       // cache_control set inside buildSystemPrompt
            messages,
            tools,                                                        // Phase 4 lifts the Phase 3 "tools absent" rule
          });
        } catch (err) {
          subscriber.error(err);                                          // typed AnthropicApiError → RxJS error channel
          return;
        }

        // Persist the assistant turn (text + tool_use blocks) and emit any text.
        const assistantBlocks = fromAnthropicMessage(response);
        subscriber.next({ kind: 'assistant_text', blocks: assistantBlocks });
        messages.push({ role: 'assistant', content: response.content as ContentBlockParam[] });

        // --- D-16: terminal stop reasons. The loop continues ONLY on 'tool_use'. ---
        switch (response.stop_reason) {
          case 'end_turn':                                                // normal finish
          case 'stop_sequence':
            subscriber.next({ kind: 'done', stopReason: response.stop_reason });
            subscriber.complete();
            return;
          case 'max_tokens':                                              // truncated — tell the user (D-16)
            subscriber.next({ kind: 'done', stopReason: 'max_tokens' });
            subscriber.complete();
            return;
          case 'refusal':                                                 // surface honestly, don't retry (D-16)
            subscriber.next({ kind: 'done', stopReason: 'refusal' });
            subscriber.complete();
            return;
          case 'pause_turn':                                              // long server-tool turn (Phase 5) — resume
            // Re-send the SAME messages unmodified (the paused assistant turn is already pushed);
            // do NOT count this against maxAgentTurns. In Phase 4 no server tool exists, so this is
            // defensive — built now because Phase 5 drops web_search onto this exact loop.
            turn--;
            continue;
          case 'tool_use':
            break;                                                        // fall through to execute tools
          default:
            subscriber.next({ kind: 'done', stopReason: response.stop_reason });
            subscriber.complete();
            return;
        }

        // --- Execute every tool_use block in this turn, collect tool_result blocks ---
        const toolUseBlocks = response.content.filter(
          (b): b is ToolUseBlock => b.type === 'tool_use',
        );
        const toolResults: ToolResultBlockParam[] = [];
        for (const tu of toolUseBlocks) {
          subscriber.next({ kind: 'tool_use_started', block: tu });       // D-01

          if (this.toolRegistry.isWriteProposal(tu.name)) {
            // D-03: NEVER block on approval. Surface the pending pill, feed a synthetic result,
            // and let the model finish. Nothing is persisted until the user approves.
            this.surfacePendingProposal(conversationId, tu);
            toolResults.push({
              type: 'tool_result',
              tool_use_id: tu.id,
              content:
                'Proposal surfaced to the user for approval and is NOT yet persisted. ' +
                'Do not assume it was saved; continue your answer using only confirmed data.',
            });
            continue;
          }

          // D-02 / D-14: read-only query_* auto-execute through ToolRegistryService,
          // dispatching to the existing domain services with BOUNDED output.
          try {
            const result = await this.toolRegistry.dispatch(tu.name, tu.input);  // bounded/summarized string
            toolResults.push({ type: 'tool_result', tool_use_id: tu.id, content: result });
            subscriber.next({ kind: 'tool_result', toolUseId: tu.id, summary: result });
          } catch (e) {
            // CHAT-11: validation/range errors come back as a readable tool_result the model can recover from.
            toolResults.push({
              type: 'tool_result',
              tool_use_id: tu.id,
              content: `Error: ${(e as Error).message}`,
              is_error: true,
            });
          }
        }

        messages.push({ role: 'user', content: toolResults });           // tool_result goes in a USER turn
      }

      // --- D-04: hit the cap. Ask for a best-effort answer with what was gathered. ---
      if (!cancelled) {
        subscriber.next({ kind: 'turn_limit', turnsUsed: maxAgentTurns });
        // (planner: one final messages.create WITHOUT tools, instructing a best-effort summary)
        subscriber.complete();
      }
    })();

    return () => { cancelled = true; };   // takeUntilDestroyed unsubscribes → loop stops
  });
}
```

> **Critical wire rule (carried from Phase 3 D-16):** `tool_result` blocks go in a **`user`** message, never an `assistant` one. This is the exact bug fixed in commit `49e275b` ("place tool_result blocks in a user turn when building API messages (Anthropic 400)"). The serializer must keep honoring it.

### Common Pitfalls
<!-- Verified against the live Anthropic tool-use, prompt-caching, token-counting, and search-results docs (2026-05-31) + the Phase 3 spec's verified SDK notes. -->

1. **Posting `tool_result` in an assistant turn → API 400 (already hit once).** The model emits `tool_use` in an *assistant* message; the matching `tool_result` blocks MUST be sent in the **next `user` message**. This exact mistake is commit `49e275b`. **Mitigation:** the loop pushes `{ role: 'assistant', content: response.content }` then `{ role: 'user', content: toolResults }` — never merge them. A serializer/loop test asserts the role of the tool_result-carrying message is `'user'`.

2. **A `pause_turn` response counted against `maxAgentTurns`, or its content mutated before resume.** Anthropic's guidance is to **re-send the conversation including the paused assistant response, unmodified**, to continue. Decrementing or rebuilding the turn breaks the resume. **Mitigation:** the `pause_turn` branch does `turn--; continue;` and pushes the assistant block exactly as received. Defensive in Phase 4 (no server tool), load-bearing in Phase 5.

3. **An unbounded `query_*` result dumps the whole dataset back through the window (D-14).** A 5-year `query_weight_entries` returning every row blows the token budget and can itself force premature summarization. **Mitigation:** every executor caps/summarizes large ranges (e.g. return aggregates + the most recent N rows, or a windowed summary) and the description tells the model the output is bounded. Validate with a "5-year range stays under X tokens via `countTokens`" test.

4. **The cache prefix churns, so every turn is a 1.25× cache *write* instead of a 0.1× read (D-15).** If `buildSystemPrompt()` reorders the key-facts header, includes a volatile timestamp mid-prefix, or conditionally emits an empty profile block in a different position, the cached prefix hash changes and you pay the write price every turn. **Mitigation:** fixed header field order; put any volatile value (e.g. "today") in a deterministic slot; keep the empty-profile omission stable (03-CONTEXT D-02/D-03); one `cache_control` breakpoint at the end of the stable prefix.

5. **A `status='pending'` write proposal round-trips to the API as a real `tool_use`, wedging the next turn.** The Phase 3 serializer already renders `pending` tool_use as a plain-text placeholder and drops `discarded` — but the Phase 4 loop now also fabricates a synthetic `tool_result` for the in-flight proposal (D-03). If either path is skipped, the model waits forever for a result that never comes. **Mitigation:** D-03 synthetic tool_result for the *current* turn's proposal; `chat-block-serializer.toAnthropicContent` plain-texts any *persisted* pending proposal on replay. Both are unit-tested.

6. **Free-text the model wrote (`Smith et al. 2019`, a bare DOI/URL) rendered as a clickable link (D-13, highest-stakes).** The model has no live source in Phase 4, so anything citation-shaped in prose is fabricated. **Mitigation:** only a `TextCitation` object whose `type` is `search_result_location` / `web_search_result_location` becomes `<a href>`; prose is rendered as plain text via a strict markdown subset with `bypassSecurityTrust*` forbidden. An adversarial regression test ("cite a study about creatine") asserts zero anchors are produced.

7. **`messages.countTokens` called per keystroke / in change detection → silent rate-limit throttle.** The endpoint is free but rate-limited. **Mitigation:** call only when constructing a request (or when memory mutates the cached prefix); store the result on the message; never bind it into a template getter.

## 4. Implementation Guidance

**Model Configuration:**

Default model: **Claude Sonnet 4.6** (`claude-sonnet-4-6`) — the price/quality sweet spot for coaching dialogue, supports `cache_control`, `search_result`, tool use, and a 1M-token context window. The model lineup advanced past Phase 3 (latest Opus is now `claude-opus-4-8`): confirm `CLAUDE_MODELS` in `models/ai-chat.model.ts` at plan time.

| Selector | Model ID | Use case | Notes |
|----------|----------|----------|-------|
| **Default** | `claude-sonnet-4-6` | All coaching turns + the agentic loop | $3/M in, $15/M out. Cache min: **1,024 tok**. 1M context. |
| Cheaper sub-task | `claude-haiku-4-5` | Summarization / classification only (4b.5) | $1/M in, $5/M out. Cache min: **4,096 tok** — the tightest floor; do not route the loop here unless the cached prefix clears 4,096. |
| Higher quality | `claude-opus-4-8` | User-selected for hard reasoning turns | $5/M in, $25/M out. Cache min: **4,096 tok**. 1M context, `effort` defaults to `high`. |

**Other parameters:**
- `max_tokens`: `aiSettings.maxResponseTokens` (default `4096`) — **always explicit** (4b.3); the SDK's auto-scaling timeout reads this value.
- `temperature`: **omit** — Anthropic's default suits conversational coaching; explicit low values produce stilted output. Revisit only if eval flags variance.
- `tools`: **present in Phase 4** — `ToolRegistryService.definitions()`. This lifts the Phase 3 "tools absent" hard rule. Add `strict: true` to each definition.
- `tool_choice`: **omit** (defaults to `{ type: 'auto' }`) — the coach should decide when to read data. A system-prompt nudge ("use the query tools to ground claims in the user's actual logs before answering") raises tool use without forcing it.
- `stream`: researcher's call (D-01 only requires per-tool-call visibility, achievable from discrete loop iterations). **Recommend non-streaming in Phase 4** — `await` the full `Message` per turn so the confidence/attribution parser runs on complete text; the live-progress feel (D-01) comes from emitting `ChatTurnEvent`s between turns. Token-by-token streaming of prose is a deferred polish.

**Core Pattern:** the `runAgenticLoop` Observable in §3 Entry Point. Key invariants: the loop body is a `for (turn < maxAgentTurns)` with a `stop_reason` `switch`; `tool_use` is the only branch that continues; write proposals get a synthetic tool_result and never block (D-03); the cap path asks for a best-effort answer (D-04).

**Tool Use:** six read-only `query_*` tools — `query_cardio_sessions`, `query_weight_entries`, `query_readings`, `query_meals_in_range`, `query_daily_totals`, `query_saved_foods` — registered in `ToolRegistryService` alongside the memory write tool. Each is a thin wrapper over the existing domain service (`CardioService`, `WeightService`, `ReadingsService`, `DietService`) returning a **bounded, summarized string** (D-14): accept `from`/`to`/filter params; for wide ranges return aggregates + the most recent N rows rather than the full set. `strict: true` on every definition. Read-only ⇒ auto-execute (D-02); the memory write tool is the only `isWriteProposal` and follows D-03. Whether the six share one `DataQueryToolExecutor` or split is the planner's call — one executor with a tool-name switch keeps the diff small.

**State Management:** unchanged data plane — everything flows through the Phase 3 stack: `ChatBlock[]` persisted in `AppData` (V5) via `StorageService`; `chat-block-serializer.ts` bridges to/from SDK wire types; SDK types stay at the `anthropic-api.service.ts` boundary (D-17). The loop's in-flight `messages: MessageParam[]` is ephemeral working state; persisted assistant turns (text + tool_use) and the synthetic/real tool_result history are written through the serializer so the next user turn replays correctly. AI memory writes still defer to the pending pill (D-03) — nothing persists without approval.

**Context Window Strategy (D-15):** two-tier.
1. **Cached prefix:** the slim `FitnessContextService` ~500-token key-facts header (today, units, profile-if-present, high-level counts / latest values) **plus** the auto-generated tools system block (≈497 tok on Sonnet 4.6) **plus** stable coaching instructions (grading contract + exemplars). The `cache_control` breakpoint sits at the end of this stable prefix. Because the header alone is below Sonnet's 1,024-token floor, the cache payoff comes from the combined stable block clearing 1,024; if the user routes to Haiku (4,096 floor) the prefix may not reach it and the cache silently no-ops (no error).
2. **Per-turn ground truth:** `query_*` results return as `tool_result` blocks (never cached — they change per query). `messages.countTokens` (model + system + messages + tools) drives the rolling-window / summarize decision each send, replacing `text.length / 4`. Summarize older turns when the count crosses the budget; keep the cache prefix byte-stable so the summary swap doesn't churn it (Pitfall 4).

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns adapted to THIS TypeScript/Angular project + the bounded agentic-loop system type — not generic.

### Structured Outputs & Runtime Validation (TypeScript)

This is a TypeScript-strict project with no Pydantic and (per CONVENTIONS) no `instructor`/`zod`-style runtime layer in the hot path. The project's equivalent of "schema-validated model output" is the **pure runtime-validation module** pattern already used by `validators.ts` and `chat-block-serializer.ts`. Two surfaces need it in Phase 4:

**(a) The confidence/attribution parser (D-09)** — the model emits an inline token contract on graded claims (the SUMMARY contract `[evidence: strong|moderate|weak|animal-only|anecdotal|speculative]`, paired with a source axis `[source: data|research]` per D-10). A stateless, DI-free module narrows assistant text into typed spans, degrading safely when a token is malformed or absent (the claim renders unbadged — never crash, never fabricate a grade):

```typescript
// services/confidence-attribution-parser.ts — PURE module, no Angular DI (mirrors validators.ts).
export type Confidence =
  | 'strong' | 'moderate' | 'weak' | 'animal-only' | 'anecdotal' | 'speculative';
export type Attribution = 'data' | 'research';

export interface ClaimSpan {
  readonly text: string;                  // the claim text with its inline tokens stripped
  readonly confidence?: Confidence;       // undefined ⇒ render unbadged (safe degradation, D-09)
  readonly source?: Attribution;          // undefined ⇒ no source marker
}

const CONFIDENCE_VALUES: ReadonlySet<string> = new Set([
  'strong', 'moderate', 'weak', 'animal-only', 'anecdotal', 'speculative',
]);
const SOURCE_VALUES: ReadonlySet<string> = new Set(['data', 'research']);

// Matches [evidence: weak] / [source: research]; case-insensitive, tolerant of spacing.
const TOKEN_RE = /\[\s*(evidence|source)\s*:\s*([a-z-]+)\s*\]/gi;

/** Stateless. Total function — any input returns a valid ClaimSpan[]; never throws. */
export function parseClaimSpans(assistantText: string): ClaimSpan[] {
  // Split on sentence/clause boundaries (planner refines), parse trailing tokens per span.
  return splitIntoClaimChunks(assistantText).map((chunk) => {
    let confidence: Confidence | undefined;
    let source: Attribution | undefined;
    let match: RegExpExecArray | null;
    TOKEN_RE.lastIndex = 0;
    while ((match = TOKEN_RE.exec(chunk)) !== null) {
      const [, axis, rawValue] = match;
      const value = rawValue.toLowerCase();
      if (axis.toLowerCase() === 'evidence' && CONFIDENCE_VALUES.has(value)) {
        confidence = value as Confidence;           // unknown grade ⇒ left undefined (no fabrication)
      } else if (axis.toLowerCase() === 'source' && SOURCE_VALUES.has(value)) {
        source = value as Attribution;
      }
      // Malformed/unknown token: silently ignored ⇒ span renders unbadged (D-09 adversarial test).
    }
    return { text: stripTokens(chunk, TOKEN_RE), confidence, source };
  });
}
```

- **How the SDK integrates:** the parser runs over `TextBlock.text` after the loop returns the assistant turn (`fromAnthropicMessage`). It is NOT fed SDK types — it takes a plain `string`, keeping the SDK boundary at the transport layer (D-17). `chat-message-list` renders the resulting `ClaimSpan[]` into badges (D-07/D-08/D-10).
- **Why not JSON / `tool_choice`-forced structured output:** inline tokens survive partial output and don't fight the prose; a forced-JSON envelope would couple grading to the whole message succeeding and break per-claim granularity (D-07). The inline-token contract is the deliberate choice (research SUMMARY).
- **Retry logic:** there is **no LLM retry** for grading — a missing/garbled token degrades to an unbadged claim (D-09); it does not trigger a re-call (re-calling would double cost and still not guarantee a token). The adversarial unit test asserts: malformed token ⇒ unbadged span, no throw, no fabricated grade. Log nothing to the API; surface nothing to the user beyond the unbadged claim.

**(b) Tool input re-validation (CHAT-11)** — any tool that accepts model-proposed values (the memory write tool) re-validates through `validators.ts` before persisting; a range failure returns a `tool_result` with `is_error: true` so the model can correct, never a silent write. Read-only `query_*` inputs are bounds-checked the same way (clamp/cap date ranges per D-14).

### Async-First Design

- **How async works here:** the SDK returns Promises (`client.messages.create`); Angular consumes Observables. The loop wraps the whole multi-turn sequence in a single `new Observable(...)` that runs an `async` IIFE and emits `ChatTurnEvent`s — Promises stay *inside* the Observable, the component subscribes once.
- **The one common mistake:** calling `client.messages.create(...)` directly in a component, or letting the SDK Promise escape the Observable and then also `from()`-wrapping it → double subscription / double-fire (Phase 3 Pitfall 8). Equally: forgetting `takeUntilDestroyed(this.destroyRef)`, so navigating away mid-loop leaves the `for` loop running and billing. **Mitigation:** the Observable's teardown sets `cancelled = true`, which the loop checks each iteration; the component pipes through `takeUntilDestroyed`.
- **Stream vs. await:** **await** the full `Message` per turn (Phase 4) so the confidence/attribution parser sees complete text and the citation guard inspects complete `citations` arrays. The live-progress UX (D-01) is delivered by emitting `tool_use_started` / `tool_result` events *between* awaited turns — not by token streaming. Token-by-token streaming of prose is deferred (it complicates inline-token parsing).

### Prompt Engineering Discipline

- **System vs. user separation:** the system prompt (built by `FitnessContextService`, cached) carries: the slim key-facts header, the grading contract (when to attach `[evidence:…]` / `[source:…]`, the 6-level taxonomy, "n=1 user data is at most `moderate`", "animal-only findings tagged `animal-only`, never human-applicable"), the citation-honesty rule ("from research = your training knowledge, label it; never write a citation as if it were a live source" — D-12), and the read-first nudge. User turns carry only the user's message. All untrusted user-asserted strings (profile sections, notes) stay inside CHAT-11 `<user_*>` delimiters.
- **Few-shot:** keep grading exemplars **inline** in the system prompt (2–3 short examples of a `strong` data-grounded claim vs. a `speculative` research claim) — they are stable and belong in the cached prefix. Do **not** dynamically retrieve examples (no retrieval layer exists; it would churn the cache).
- **Token budget:** `max_tokens` is **always explicit** (`4096` default). Never unbounded in production — it sets the SDK timeout and caps per-turn cost. The tools system block adds ≈497 tokens on Sonnet 4.6; budget for it.

### Context Window Management

System type is the bounded agentic loop (Hybrid), so this is conversation-summarization + per-turn-retrieval, not RAG chunking:
- **Per-turn retrieval keeps the window small:** `query_*` results are bounded (D-14) and returned as `tool_result` blocks, not stuffed into the system prompt. Token cost grows with the *answer*, not the dataset.
- **Rolling-window summarization:** `messages.countTokens` (not `text.length/4`) decides when to summarize older turns; the running summary replaces them as a synthetic text pair. `tool_use`/`tool_result` blocks inflate history faster than plain chat, so the count check runs every send.
- **Cache stability is a window concern too:** summarizing must not touch the cached prefix order (Pitfall 4) — the summary lives in the message body, the prefix stays byte-stable.
- **Cap, not crash (D-04):** `maxAgentTurns` (default 10) bounds the loop; hitting it asks for a best-effort answer and surfaces an honest notice, never silent truncation.

### Cost and Latency Budget

- **Per-turn cost (Sonnet 4.6, $3/M in · $15/M out):** a grounded coaching answer that fires ~3 `query_*` calls runs ~4 model round-trips. Rough envelope: cached system prefix read ≈ (prefix tokens × 0.1 × $3/M); fresh per-turn input (tool_results + history) a few K tokens; output ~500–1,500 tokens. A typical multi-tool answer lands on the order of **~1–3¢**; a long 10-turn capped session a few times that. The cap (D-04) is the hard ceiling on a runaway loop.
- **Caching:** `cache_control: ephemeral` on the stable prefix turns repeat-turn system cost from 1× to **0.1×** input — the single biggest lever, and the reason the prefix must stay stable (Pitfall 4). 5-minute TTL is fine for an interactive session; the 1-hour TTL (2× write) is not worth it for single-user bursty chat.
- **Cheaper-model routing (4b.5):** route **summarization** (the rolling-window compaction) and any future **classification/routing** sub-tasks to `claude-haiku-4-5` ($1/M in). Keep the main coaching loop on Sonnet 4.6 — the grading + cross-domain reasoning is where quality matters. Note Haiku's 4,096-token cache floor: a Haiku summarization call with a short prompt won't cache, which is fine (it runs rarely).
- **Semantic caching:** not applicable for single-user bursty chat — there is no cross-user request overlap to exploit; exact-match prompt caching (above) is the relevant mechanism.

## 5. Evaluation Strategy

> **Tooling reality check (read first).** The reference framework's default eval stack — Arize Phoenix tracing, RAGAS metrics, Langfuse/LangSmith hosted platforms, OpenTelemetry collectors — is **consciously overridden here and does NOT apply.** Those are Python / server-side tools that assume a backend, a telemetry sink, and a multi-user request stream. This system is a **browser-only, single-user Angular 18 + TypeScript app** making **stateless** Anthropic calls with the *user's own* API key and **no backend, no CI eval server, and no telemetry pipeline** (per PROJECT.md constraints + Section 2). Forcing Phoenix/RAGAS would add an unusable, unrunnable abstraction for zero gain — exactly the anti-pattern Section 2 rejects for agent frameworks.
>
> The honest, fit-to-stack eval architecture is **three layers**, in descending order of strength/cheapness:
> 1. **Code-based deterministic evals (Karma + Jasmine `*.spec.ts`)** — the dominant layer and the CI gate. Several Phase 4 success criteria are literally unit-testable assertions over **pure modules** (the confidence/attribution parser D-09, the citation-link guard D-13, the loop terminal-stop-reason switch D-16, bounded `query_*` output D-14, token-counting/cache behavior D-15). These run under the existing `ng test --no-watch` with no new dependency.
> 2. **In-repo reference-fixture set, run manually/periodically against the live API** — 10–20 TypeScript/JSON prompt fixtures (below) the developer-user runs against their real Anthropic key to evaluate the subjective dimensions code can't reach (evidence-grade defensibility, scope discipline, sycophancy resistance, disclosure honesty). Not a CI gate (it costs real tokens and is non-deterministic); a pre-merge / pre-release manual check.
> 3. **Offline LLM-judge script (developer-run, calibrated)** — a small standalone Node/TS script that calls the Anthropic API *as a judge* over the fixture transcripts, scoring the subjective dimensions against the rubrics below. Calibrated against the developer-user's own labels (target ≥ 0.7 agreement) before its scores are trusted. **NOT a hosted platform** — just `messages.create` with a judge prompt.

## 7. Production Monitoring

> "Production" here is **one informed adult running the app locally on their own machine with their own API key** — there is no fleet, no server, no telemetry backend, and (per PROJECT.md) none is to be added. Monitoring is therefore **lightweight, in-app, dev-only client-side logging** for the single user, plus that user's own review of saved conversations. No hosted tracer.

**Tracing Tool:** **None hosted — Arize Phoenix / Langfuse / LangSmith explicitly overridden** (browser-only, single-user, stateless calls, no backend; see §5 reality-check). In place of a tracer: **dev-only `console`/in-memory logging at the `anthropic-api.service.ts` transport boundary** (the sole SDK consumer, D-17), capturing per-turn `Usage` (`input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`), `stop_reason`, turn index, and `maxAgentTurns`-hit flag. Gated behind a dev flag so it is stripped from production builds. The persisted `ChatBlock[]` conversation history *is* the durable trace the developer-user reviews.

**Key Metrics to Track** (dev-logged at the transport boundary, reviewed by the single user):
1. **Cache-read ratio** — `cache_read_input_tokens / (cache_read + cache_creation)` per turn. Should trend toward cache *reads*; a low ratio means the prefix is churning (Pitfall 4 / E7).
2. **Turns-per-answer & maxAgentTurns-hit rate** — how often the loop runs long or hits the cap (D-04). A rising cap-hit rate signals tool/prompt inefficiency or a runaway pattern.
3. **Per-answer token cost** — `input + output` tokens per coaching answer (the §4 cost envelope: a typical multi-tool answer ~1–3¢). Surfaces unbounded-output regressions (E6).
4. **Terminal-stop-reason distribution** — counts of `end_turn` vs `max_tokens` vs `refusal` vs cap. A spike in `max_tokens`/`refusal` is a quality/UX signal.
5. **Unbadged-claim rate** — share of claims the parser left unbadged (D-09 safe degradation). A rising rate means the model is dropping the `[evidence]`/`[source]` contract (system-prompt drift).

**Alert Thresholds** (single-user, so "alert" = a visible dev-console warning / self-review trigger, not a pager):
- **Cache-read ratio < ~0.5 across a session** → investigate prefix stability (E7 / Pitfall 4).
- **maxAgentTurns-hit on > ~20% of answers** → tools too granular or prompt under-guiding; revisit `query_*` design or the read-first nudge.
- **Per-answer cost materially above the ~1–3¢ envelope** → suspect an unbounded `query_*` result (E6 / D-14).
- **Unbadged-claim rate climbing** → the grading contract is eroding; re-tighten exemplars and add a fixture.
- **Any `<a href>` produced from non-`TextCitation` content** → treat as a Critical regression; the E1 guard must hold (this should be caught by `ng test` before it ever reaches a session).

**Smart Sampling Strategy:** signal-weighted self-review by the developer-user (the §1b transparency-auditor hat). Prioritize for review the saved conversations where: a tool-use limit was hit, a `refusal`/`max_tokens` terminal reason fired, the user asked a **leading** question (sycophancy risk, E11), the turn involved **glucose/keto/BP** advice (scope-drift + mis-grading risk, E10/E9), or a `from research` claim appeared (citation-honesty + over-grading risk, E1/E9). These same flagged transcripts feed back into the reference-fixture set (§5), closing the flywheel.
