# Phase 4 — UI Design Contract

> Visual and interaction contract for Phase 4: Agentic Loop + Citation UI. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **What this phase adds to the chat surface:** live per-tool-call progress (D-01), collapsed `tool_use`/`tool_result` disclosures (D-05/D-06), per-claim confidence + source badges (D-07/D-08/D-10), a data-claim → tool-call traceability affordance (D-11), the citation-link render guard (D-13), and a graceful turn-limit notice (D-04). It extends the Phase 3 block-aware `@switch` render in `chat-message-list.component.ts` — it does not rebuild it.
>
> **Hard scope rule (from 04-CONTEXT):** No web-search citations are produced this phase (Phase 5). The renderer ships only the *rule* and the plain-text guard. Phase 4 rendering MUST leave room for the Phase 5 structured-citation upgrade without rework (D-12).

| Property | Value |
|----------|-------|
| Tool | none (Angular 18 project — shadcn gate not applicable; React/Next/Vite only) |

| Component library | none (standalone Angular components, semantic HTML, no CSS framework — locked by CLAUDE.md) |

**Styling approach (locked from CLAUDE.md):** Minimal custom CSS, semantic HTML, no CSS framework. Each new/extended standalone component carries its own `styles: [...]` array. Existing global utility classes in `src/styles.css` (`.btn`, `.btn-primary`, `.btn-secondary`, `.btn-sm`, `.empty-state`, `.mt-*`, `.mb-*`) are reused. Phase 4 introduces no new global classes — all new visual surface lives in component-scoped `styles`.

**Existing components/surfaces to compose or extend (NOT re-implement):**
- `<app-chat-message-list>` (`src/app/features/chat/chat-message-list.component.ts`) — the `@switch (block.type)` render is **extended**, not rebuilt. Phase 3 left `tool_use` → `<app-pending-pill>` and `tool_result` → static placeholder. Phase 4 supplies the real `tool_result` collapsible viewer and the in-text confidence/source badge render inside the `'text'` branch.
- `<app-pending-pill>` (`src/app/features/chat/pending-pill.component.ts`) — receives its first **real** proposals this phase (D-03). Visual contract is unchanged from Phase 3; only the resolved-state timestamp gains a real `resolvedAt` (Phase 3 stubbed `new Date()`).
- `<app-error-state>` (`src/app/shared/error-state.component.ts`) — surfaces a transport/API failure of the agentic loop (network drop, 401, non-recoverable SDK error).

**New surfaces introduced this phase (all inline in component templates — no premature extraction):**
- Tool-call disclosure (collapsed `<details>` row, one per `tool_use` — D-06)
- Confidence badge + source badge (inline chips after a claim — D-07/D-08/D-10)
- Turn-limit notice (one-line in-stream system notice — D-04)
- Citation-link guard (a render rule, not a visible element — D-13)

## Typography

Declared from `src/styles.css` + existing chat components. Phase 4 introduces **no new sizes** — exactly the **4 sizes** already in the system are used: 14px, 16px, 20px, 28px (plus the existing 12px / 0.75rem role-tag micro-label and 11px / 0.7rem timestamp, both pre-existing in `chat-message-list.component.ts:99–127` and preserved verbatim).

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body / message text | 16px (1rem) | 400 (regular) | 1.5 |
| Tool-disclosure summary label | 14px (0.875rem) | 600 | 1.5 |
| Tool-disclosure expanded detail (params, result) | 14px (0.875rem) | 400 | 1.5 |
| Confidence / source badge label | 14px (0.875rem) | 600 | 1.2 |
| Turn-limit notice | 14px (0.875rem) | 400 | 1.5 |
| Heading h1 (page — unchanged) | 28px (1.75rem) | 600 | 1.2 |

**Weights used:** exactly two — 400 (body, disclosure detail, turn-limit notice) and 600 (badge labels, disclosure summary). The single legacy 500 in the global `.btn` class is preserved as-is; do not introduce new uses (matches the Phase 3 rule).

**Phase 4-specific typography rules:**
- Tool-disclosure collapsed summary (`📊 Read 38 weight entries · Jan 1–May 31`): 14px / 600 / 1.5. The leading glyph is part of the text content (not a CSS pseudo-element) so it is screen-reader-visible.
- Tool-disclosure expanded body: the raw structured detail (tool name, formatted input params, formatted result table/JSON) renders at 14px / 400 / 1.5 inside a `<pre>` with `white-space: pre-wrap` (matches the existing `.tool-result-placeholder` and pending-pill `<pre>` voice).
- Confidence/source badge: 14px / 600 inline chip; the chip text label is the taxonomy word (`strong`, `weak`, `animal-only`, etc.) or source word (`your data`, `research`) — never abbreviated to a single letter (D-08 "text label always").
- Turn-limit notice: 14px / 400, muted color, italic optional — matches the `.history-item-notes` voice (`src/styles.css:191–196`).
- A claim the parser left **unbadged** (malformed/absent token — D-09) renders as plain 16px / 400 / 1.5 body text with no chip. This is the safe-degradation visual: no placeholder, no error glyph, just unannotated prose.

## Color

Existing palette preserved. **No new hex is introduced for chrome.** Phase 4 DOES introduce a small, bounded set of **semantic state colors** for the confidence/source badges — these are the one place new color is justified because the requirement (CHAT-07 / D-08, Pitfall 10) is "low-confidence states must be visually distinct." Each badge color is paired with an icon + text label, so color is never the only channel.

### Core palette (60/30/10 — unchanged from Phase 3)

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#f5f5f5` (app background), `#ffffff` (card surface), `#f0f0f0` (assistant message bubble), `#f8f9fa` (dimmed disclosure surface) | Backgrounds, message bubbles, collapsed/expanded disclosure surface |
| Secondary (30%) | `#2c3e50` (primary text/headings), `#7f8c8d` (muted secondary text), `#ddd` (borders) | Body text, disclosure borders, muted timestamps + turn-limit notice |
| Accent (10%) | `#3498db` | **Reserved-for list below — never "all interactive elements"** |
| Destructive | `#e74c3c` (hover `#c0392b`) | `<app-error-state>` (loop transport failure) only |

**Accent (`#3498db`) reserved for (explicit list — Phase 4):**
1. `<form>` input focus border + box-shadow on the chat input (preserved from existing `.form-group input:focus`)
2. Pending-pill primary action button "Save to memory" / "Apply update" (existing `.btn-primary`, unchanged from Phase 3)
3. The **data-claim → tool-call traceability link** (D-11): the small "view source" affordance on a `from your data` claim that anchors to its originating tool disclosure renders as an accent-colored inline text link (`#3498db`, underline on hover). This is the only NEW accent use in Phase 4.

**Accent explicitly NOT used for:**
- Confidence/source badges (they use the semantic state palette below, not accent)
- Tool-disclosure summary rows or chevrons (neutral `#2c3e50` text on `#f8f9fa`)
- Turn-limit notice (muted `#7f8c8d`)
- User message bubble (keeps existing `#3498db` background — this is a pre-existing use, preserved, not a new reservation)

### Confidence badge semantic palette (NEW — bounded; color is one of three channels)

The 6-level taxonomy collapses to **two visual tiers** so a skimming user instantly tells calm from alert (D-08). Within each tier the **icon + text label** disambiguate the exact grade; color signals only the tier.

| Tier | Grades | Background | Text/Border | Icon (Unicode, screen-reader-visible) |
|------|--------|-----------|-------------|----------------------------------------|
| Calm / higher-confidence | `strong`, `moderate` | `#eef6ec` (pale green) | `#2e7d32` (forest green) | `✓` (strong) · `≈` (moderate) |
| Alert / lower-confidence | `weak`, `animal-only`, `anecdotal`, `speculative` | `#fdf3e7` (pale amber) | `#b9770e` (amber-brown) | `⚠` (all four; the text label distinguishes them) |

- Pale-green `#eef6ec` / `#2e7d32` and pale-amber `#fdf3e7` / `#b9770e` are the only new hex values in Phase 4. They are chosen to read as calm-vs-caution at a glance while staying inside the muted, low-saturation voice of the existing palette (no pure `#0f0`/`#f00`). Exact final hex may be nudged by the executor for `color-contrast`, but the calm/alert tier split and the icon+label pairing are LOCKED.
- `color-contrast` axe-core rule remains deferred to Phase 5 QUAL-08 (`disableRules: ['color-contrast']`), consistent with the Phase 1 / Phase 3 pattern — but the badge palette above is chosen with WCAG AA text contrast in mind so the Phase 5 sweep is a confirmation, not a redesign.

### Source badge semantic palette (NEW — paired with confidence, D-10)

Source is the second axis. It is distinguished by **icon + text label** primarily; color is a subtle neutral so it does not compete with the confidence tier.

| Source | Label text | Icon | Treatment |
|--------|-----------|------|-----------|
| from your data | `your data` | `📈` | Neutral chip: `#f0f0f0` background, `#2c3e50` text. Carries the D-11 traceability link. |
| from research | `research` | `📚` | Neutral chip: `#f0f0f0` background, `#2c3e50` text, **plus** the literal qualifier text `general knowledge — not a live source` rendered adjacent (D-12). Zero hyperlinks (D-13). |

**State-color rules (color is never the only indicator — CLAUDE.md a11y, preserved from Phase 3 D-13 rule):**
- Every confidence badge carries color **+ icon (`✓`/`≈`/`⚠`) + text label** (D-08 triple-encoding). A `from research · speculative` claim (pale-amber `⚠ speculative` + neutral `📚 research`) is visually unmistakable from a `from your data · strong` claim (pale-green `✓ strong` + neutral `📈 your data`).
- Every source badge carries icon **+ text label** (`📈 your data` / `📚 research`), never color alone.
- An unbadged claim (D-09 safe degradation) carries no chip and no color — it is plain prose, deliberately.

## Focal Point Declaration

Each new/changed surface declares one focal point — where a sighted user's eye lands first and where a keyboard user lands after a transition.

| Surface | Focal point | Mechanism |
|---------|-------------|-----------|
| Chat stream **while the agentic loop is running** | The **most recent live tool-call row** (`tool_use_started` — "Reading your weight entries…"). The stream auto-scrolls to keep the in-flight row in view so the user watches evidence being gathered (D-01). | Reuse existing `scrollToBottom()` in `chat-message-list.component.ts:184–189`, fired on each `ChatTurnEvent`. No new focus steal — focus stays on chat input. |
| Chat stream **when the loop emits a write proposal mid-answer** | The **pending-pill primary action button** (existing Phase 3 focal point — D-03 does not change it). | Existing `<app-pending-pill>` `ViewChild('primaryAction')` + `setTimeout(focus, 0)`. |
| Chat stream **when the loop completes normally** | Chat input textarea retains focus (existing behavior). | Existing — no change. |
| Chat stream **when `maxAgentTurns` is hit** | The turn-limit notice is announced via `aria-live="polite"` but does NOT steal focus; focus returns to chat input so the user can immediately reply/retry. | `role="status"` + `aria-live="polite"` on the notice element. |
| A collapsed tool disclosure | Its `<summary>` is keyboard-focusable in DOM order; no auto-focus (the prose answer is the primary content, the disclosure is opt-in audit). | Native `<details>`/`<summary>` semantics. |

## Copywriting Contract

All copy below is LOCKED. The voice matches Phase 3 (plain, second-person, honest-about-uncertainty). Dynamic tokens are in `{braces}`.

### Live tool-call progress (D-01) — in `chat-message-list` `tool_use`/`tool_result` render

| State | Visible copy |
|-------|--------------|
| Tool call in flight (collapsed summary, `tool_use_started`) | `{glyph} {present-tense action}…` — e.g. `📊 Reading your weight entries…` |
| Tool call resolved (collapsed summary, `tool_result`) | `{glyph} {past-tense summary} · {range or count}` — e.g. `📊 Read 38 weight entries · Jan 1–May 31` |
| Disclosure expand affordance (`<summary>` accessible name) | `Show what the AI looked at: {summary}` |
| Disclosure expanded section heading | `Tool: {tool_name}` |
| Disclosure expanded params label | `Query:` |
| Disclosure expanded result label | `Result:` |

**Per-tool present/past summary verbs (LOCKED — the summary string is derived from the actual `tool_result`, never free-authored by the model — E12):**

| Tool | In-flight | Resolved |
|------|-----------|----------|
| `query_cardio_sessions` | `🏃 Reading your cardio sessions…` | `🏃 Read {n} cardio sessions · {range}` |
| `query_weight_entries` | `⚖️ Reading your weight entries…` | `⚖️ Read {n} weight entries · {range}` |
| `query_readings` | `🩺 Reading your health readings…` | `🩺 Read {n} readings · {range}` |
| `query_meals_in_range` | `🍽️ Reading your meals…` | `🍽️ Read {n} meals · {range}` |
| `query_daily_totals` | `📊 Reading your daily totals…` | `📊 Read daily totals · {range}` |
| `query_saved_foods` | `📚 Reading your saved foods…` | `📚 Read {n} saved foods` |

> `{range}` and `{n}` are computed by the renderer from the tool input/result — NOT from model prose. If a count is unavailable, the renderer omits the `· {…}` clause rather than guessing (transparency over false precision).

### Loop terminal-state notices (D-16)

| Stop reason | Visible copy |
|-------------|--------------|
| `max_tokens` (truncated) | `This answer was cut off at the length limit. Ask me to continue if you'd like the rest.` |
| `refusal` | `I'm not able to answer that one.` (rendered as a plain assistant message — honest, no raw error) |
| `end_turn` / `stop_sequence` | (no notice — normal completion) |
| `pause_turn` | (no notice — resumes silently; defensive for Phase 5) |

### Loop transport failure (network / 401 / SDK error)

| Element | Copy |
|---------|------|
| Error-state title (via `<app-error-state>`) | `The AI request didn't go through` |
| Error-state message | `Something interrupted the request. Check your connection and API key, then try again.` |
| Retry button (existing `<app-error-state>` retry) | `Retry` |

> Full 401-specific "rotate / re-enter key" UX is QUAL-07 (Phase 5). Phase 4 surfaces a generic recoverable error with Retry; it must not crash or log-only.

### Citation guard (D-13) — a render RULE, not user-facing copy

No user-facing copy. The rule: any author-year string (`Smith et al. 2019`), bare DOI, or URL the model writes **in prose** renders as **plain inert text** — never an `<a href>`. Only a structured `TextCitation` (`search_result_location` / `web_search_result_location`) may become a link, and none exist in Phase 4. `bypassSecurityTrust*` and markdown autolinking of prose are forbidden.

### Destructive actions in this phase

| Action | Confirmation approach |
|--------|----------------------|
| Discard a pending pill (now driven by real proposals — D-03) | **No confirm** (unchanged from Phase 3). Discard is low-friction reject; the resolved badge `✗ Discarded {time}` is the audit trail. |
| Approve a memory/profile write proposal | **The pill IS the confirmation** (confirm-before-write — D-03). No second dialog. Persistence happens only on explicit approve click; nothing the loop proposed is written without it. |

> Phase 4 introduces **no new destructive flows**. `query_*` tools are strictly read-only (D-02) — they cannot mutate data, so they have no confirmation surface at all.

**No routes added.** Phase 4 is entirely within the existing `/chat` route surface. The agentic loop renders into the existing `<app-chat-message-list>` inside `chat-page.component.ts`. Hash routing (`withHashLocation()`) and the top nav are unchanged.

## Accessibility Contract (CLAUDE.md "Accessibility basics" + Phase 1 axe-core gate)

**Every new/extended component asserts `expectNoSeriousA11yViolations(fixture)` after representative render.** Severity gate: `serious | critical` (Phase 1 D-08). `color-contrast` deferred to Phase 5 QUAL-08 via `disableRules: ['color-contrast']` (matches Plan 01-08 / Phase 3 pattern).

**Specific a11y rules for Phase 4 surfaces:**

| Surface | Rule |
|---------|------|
| Tool-call disclosure | Native `<details>`/`<summary>` (not `<div role="button">`); `<summary>` has a descriptive accessible name (`Show what the AI looked at: {summary}`); keyboard-toggleable by default; `min-height: 44px` touch target. |
| In-flight tool row | `role="status"` `aria-live="polite"` so a screen-reader user hears "Reading your weight entries…" as the loop progresses, then the resolved summary — the live-progress promise (D-01) reaches non-sighted users too. |
| Confidence badge | `<span>` with `aria-label="Confidence: {grade}"`; the visible glyph (`✓`/`≈`/`⚠`) is real text content (screen-reader-visible), NOT a CSS pseudo-element or background image. Color + icon + text triple-encoding (D-08). |
| Source badge | `<span>` with `aria-label="Source: from your data"` / `"Source: from research — general knowledge, not a live source"`; visible icon is real text content. |
| Data-claim traceability link | Native `<a href="#tooluse-{id}">` with `aria-label="View the data this claim is based on"`; the target disclosure has the matching `id`. Keyboard-activatable. |
| Turn-limit / terminal notice | `role="status"` `aria-live="polite"`; does not steal focus. |
| Loop transport error | `<app-error-state>` already uses `role="alert"` `aria-live="assertive"` — reused as-is. |
| Citation guard | Verified by spec (E1): adversarial "cite a study" input → `querySelectorAll('a')` returns zero anchors for model-authored prose. This is an a11y *and* safety assertion. |

**Color is never the only indicator (preserved rule):**
- Confidence tier: color **+** icon (`✓`/`≈`/`⚠`) **+** text label.
- Source: icon (`📈`/`📚`) **+** text label (color is a subtle neutral, not the signal).
- In-flight vs resolved tool row: present-tense "…" text + pulsing cue **vs** past-tense summary + count — distinguished by text, not color.

**Keyboard navigation rules:**
- Tool-call disclosures are focusable in DOM order (execution order); Enter/Space toggles (native).
- "view source" traceability links are focusable in DOM order; Enter activates and moves focus to the target disclosure.
- Pending-pill keyboard contract unchanged from Phase 3 (Save → Edit → Discard in DOM order).
- No custom arrow-key handlers (out of scope per CLAUDE.md "Function over form").

**Focus management during the loop:**
- The loop must NOT yank focus on every `ChatTurnEvent` (that would trap a keyboard user). Focus stays on the chat input; live progress reaches screen readers via `aria-live` regions, not focus moves.
- Exception: when a write proposal surfaces mid-loop, the pending-pill primary action receives focus (existing Phase 3 behavior, D-03) — this is the one intentional focus move, and focus returns to chat input on resolve.
