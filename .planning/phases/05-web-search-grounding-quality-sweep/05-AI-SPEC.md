## 1. System Classification

**System Type:** Conversational (tool-using agentic coach). Phase 5 adds ONE Anthropic server-side tool (`web_search_20250305`) to the existing `tools[]` array on the Phase 4 bounded `while(stop_reason === 'tool_use')` `runAgenticLoop`. No new system class — it is a read-only, opt-in capability extension of the existing conversational coach.

**Description:**
A single-user, local fitness-coaching chat. The user logs cardio, weight, health readings, and diet locally (LocalStorage, nothing leaves the device); a Claude-backed coach answers questions, reading the user's own data through Phase 4's read-only `query_*` client tools and persisting notes through the `memory` write tool. Phase 5 lets the coach — **only when the user opts in via `/settings` (off by default)** — reach for live web sources to ground genuinely current or research-grounded questions (recent studies, current guidelines). Anthropic executes the search server-side and returns `web_search_tool_result` + `web_search_result_location` citation blocks inline; the client never dispatches the tool. "Good" is: the coach grounds research claims in real, clickable (`https:`-only) live sources rendered as inline footnotes + a per-message Sources list, **visibly distinguishes a grounded-and-linked claim from an un-grounded "from research" claim** (the honest reconciliation of "attribute research" vs "never fabricate citation links"), bounds cost via a user-visible `webSearchMaxUses` cap, and never lets free-text prose become a hyperlink. The non-AI quality sweep (CRUD parity, quota safety, multi-tab safety, CSP, 401 rotation, a11y, archival, mutation testing) is out of scope for THIS contract — it is the planner's; this AI-SPEC governs only the web-search-grounding behavior (RESCH-01/02/03).

**Critical Failure Modes:** (the behaviors that absolutely cannot go wrong)
1. **Fabricated citation links.** A free-text author-year / DOI / URL string the model writes in prose becomes an `<a href>`. The trust mechanism collapses (research Pitfall 1: 14–95% LLM citation fabrication). ONLY structured `web_search_result_location` / `search_result` blocks may become links, gated to `https:`. Must hold across the full matrix: web-search OFF and web-search ON (D-09).
2. **Grounded/un-grounded confusion.** A skimming user cannot tell a live-source-backed "from research · grounded" claim (with footnote link) from an un-grounded training-knowledge "from research" claim (plain text, no link). The honest two-axis source labeling (D-04) is the whole point — collapsing the distinction is silent misrepresentation.
3. **Privacy leak via search query.** With web search enabled, the model formulates query strings that leave the device. Embedding the user's personal/health specifics or per-entry free-text notes into a search query egresses PII the app's whole posture exists to keep local (D-10). The system prompt must discourage this; `validators.ts` re-validation of model-proposed tool args stays binding (CHAT-11).
4. **Loop wedge on a server-tool / `pause_turn` turn.** The agentic loop must treat a turn containing `server_tool_use` / `web_search_tool_result` as a normal turn to render and continue (honoring `pause_turn` resume, Phase 4 D-16), never as a client `tool_use` to dispatch through `ToolRegistryService`. Mishandling wedges the loop or double-bills.
5. **Unbounded cost.** The `webSearchMaxUses` cap must be wired to the request AND visibly surfaced near the toggle so the user can see the per-message search ceiling (success-criterion 1, D-06). A silent or unbounded cap is a cost-control failure.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Consumer health & wellness — specifically evidence-graded fitness/nutrition self-coaching (general-wellness, **not** clinical decision support, **not** a medical device). The defining product decision (PROJECT.md Key Decisions): NO clinical disclaimers and NO clinical guardrails. The trust mechanism is instead **source attribution + per-claim confidence labels** (Phase 4 taxonomy: strong / moderate / weak / animal-only / anecdotal / speculative). Phase 5 makes the "from research" axis *honest about provenance*: a research claim is now either **grounded** (backed by a live `web_search_result_location`, rendered as a clickable `https:` footnote) or **un-grounded** (training knowledge, plain inert text, no link). Because there are no disclaimers to fall back on, **the quality and honesty of evidence grading — and now the integrity of the live citation — IS the safety mechanism.**

**User Population:** A single, sophisticated, non-clinician individual (the developer/owner) self-coaching against their *own* locally-logged health data — cardio, weight, blood pressure, blood glucose, ketones, and diet/macros. Not a patient under care, not a population of strangers, not a clinician using decision support. The user reads coaching prose and decides whether to change their own diet, training load, or how they interpret their own vitals trends. They opt in to web search deliberately (OFF by default); they are health-literate but not trained to spot a citation-claim mismatch or an over-extrapolated animal study on their own.

**Stakes Level:** **High** (honestly calibrated — not Critical). Justification, both directions:
- *Why not Medium:* The output is health/nutrition/exercise guidance a layperson **acts on**, including how they interpret blood glucose, ketone, and blood pressure trends — and there are deliberately **no clinical guardrails or disclaimers** softening it. A confidently-stated, mis-graded, or falsely-"grounded" claim can drive a real dietary or training change with no safety net. The trust scaffolding (confidence labels + citation integrity) is load-bearing, which raises the bar on the AI behavior this phase ships.
- *Why not Critical:* This is single-user **self-coaching of one's own data**, not a clinical decision-support product, not diagnosis, not treatment of others, not a regulated medical device, and not population-scale deployment. One sophisticated user acting on their own record bounds the blast radius. Critical would imply clinical/safety-of-others consequences this product explicitly does not occupy.

**Output Consequence:** Acting on the coaching changes real behavior — diet composition, training volume/frequency, or how the user reads their own vitals. The Phase-5-specific consequence: a claim wearing a **grounded footnote link borrows the authority of a real source.** If that link does not actually support the claim (citation-claim mismatch), or lends a real-looking source to a weak/preliminary/animal-only finding, the user updates on borrowed false confidence — the exact failure the "source + confidence instead of disclaimers" bet is supposed to prevent. The inverse also matters: a real, well-graded grounded citation is the payoff that makes the no-disclaimer posture defensible.

### What Domain Experts Evaluate Against

> Practitioner-language rubric ingredients centered on **evidence grading + citation integrity** for grounded web claims — the substance this phase delivers. These are the building blocks the `gsd-eval-planner` turns into measurable rubrics (§5).

**Dimension: Citation–claim support match (does the linked source actually say this?)**
Good (expert accepts): Every grounded `[n]` footnote points to a live source whose `cited_text` genuinely supports the specific sentence it is attached to; the claim does not say more than the source does.
Bad (expert flags): A footnote is attached to a sentence the source does not actually support — a real, clickable, authoritative-looking link laundering an unsupported claim (citation-claim mismatch). Worse than no citation, because the link manufactures false confidence.
Stakes: Critical
Source: LLM citation-integrity research — GPT-4o produced ~20% fully fabricated and ~two-thirds fabricated-or-inaccurate citations in mental-health literature reviews, and "reference accuracy" is proposed as a direct measure of inherent misinformation in medical chatbots ([PMC – topic familiarity & citation fabrication](https://pmc.ncbi.nlm.nih.gov/articles/PMC12658395/); [PMC – reference accuracy as a misinformation metric](https://pmc.ncbi.nlm.nih.gov/articles/PMC12829275/); [Exploration Pub – confabulated references contaminating the literature](https://www.explorationpub.com/Journals/em/Article/1001385)).

**Dimension: Evidence-quality honesty (is the grading faithful to the study design?)**
Good (expert accepts): The confidence label matches the actual study design behind the source — a single observational/cohort finding is labeled `weak`/`moderate`, not `strong`; "settled science" / "strong" is reserved for systematic reviews, meta-analyses, or convergent RCT evidence; mechanistic or animal evidence is graded `animal-only`, never presented as established human guidance.
Bad (expert flags): A single observational study (or a preliminary finding) presented as settled fact; an `animal-only` mechanism dressed up as `strong`; the confidence label drifting *upward* simply because a live link now exists ("it has a source, so it must be strong").
Stakes: High
Source: Nutrition-science evidence hierarchy — systematic reviews/meta-analyses > RCTs > prospective cohort > observational > in vitro/animal; observational links cannot establish cause-and-effect and animal/mechanistic evidence only raises confidence when it converges with human outcomes ([Eufic – levels of evidence in nutrition research](https://www.eufic.org/en/understanding-science/article/the-levels-of-evidence-in-nutrition-research); [Advances in Nutrition / PMC – limitations of observational evidence](https://pmc.ncbi.nlm.nih.gov/articles/PMC3884102/); [Kerry Health & Nutrition Institute – nutrition study designs](https://khni.kerry.com/articles/food-science/understanding-nutrition-research-study-designs/)).

**Dimension: Grounded vs un-grounded distinguishability (can a skimming reader tell a linked claim from a training-knowledge claim?)**
Good (expert accepts): A live-source-backed claim renders visibly distinct ("from research · grounded" + footnote link); an un-grounded training-knowledge "from research" claim stays plain inert text with no link — and the distinction survives a skim, not just careful reading (color is never the only channel).
Bad (expert flags): Both render identically, so the reader cannot tell which claims have a live source behind them and which are the model's unverified recall — silent misrepresentation of provenance.
Stakes: Critical
Source: Health-literacy research — laypeople routinely fail to distinguish strength/source of treatment claims and overstate causal inference from media-style presentation; the provenance signal must be in the rendering, not left to reader inference ([PMC – Norwegian public's ability to assess treatment claims](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC10995534/); [PMC – CLAIMS systematic review of causal-language overstatement](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC5976147/)). Plus the project's own "color is never the only state indicator" a11y rule (CLAUDE.md) and D-04.

**Dimension: No overstatement of preliminary / single-source findings (recency vs authority handled honestly)**
Good (expert accepts): A recent, single, or preliminary finding is framed as emerging — "one recent study suggests…", positioned against the broader body of evidence — and recency is not silently treated as authority. A newer weak source does not override stronger established consensus.
Bad (expert flags): A single fresh study (the kind web search surfaces well) presented as if it overturns or settles a question; "from research" treated as a uniform stamp regardless of whether the source is a meta-analysis or a single preprint; fast-moving nutrition headlines stated with unwarranted certainty.
Stakes: High
Source: Media/health-literacy research on single-study reporting — coverage of a single study routinely fails to contextualize it within an emerging body of knowledge, and shared academic/media articles systematically overstate strength of causal inference ([PMC – using media claims to teach evidence-based healthcare](https://pmc.ncbi.nlm.nih.gov/articles/PMC8479747/); [PMC – CLAIMS: causal language & strength of inference](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC5976147/)).

**Dimension: Personal-health-data containment in outbound queries (does the search leak PII?)**
Good (expert accepts): Web-search query strings are phrased in *general* research terms ("recent guidelines on resistance-training frequency"); the user's specific conditions, vitals values, or per-entry free-text notes never enter a query that egresses the device.
Bad (expert flags): The model embeds the user's personal/health specifics or per-entry note free text into a search query ("is keto safe for someone with [user's specific condition]"), widening the one outbound channel the app's local-only posture exists to keep narrow.
Stakes: High
Source: Project privacy posture (PROJECT.md Core Value: "nothing leaving the machine except the AI request"; D-10; CHAT-11 tool-arg re-validation) — domain-relevant because health PII is the sensitive payload and web search is the new egress surface.

### Known Failure Modes in This Domain

> How citation/evidence failures manifest specifically in lay health self-coaching — not generic "hallucination," but the concrete shape it takes here.

1. **Citation-claim mismatch acted on as a dietary/training change.** A grounded footnote links to a real source that does not actually support the attached sentence; the user, trusting the visible link, changes their diet or training on a claim the source never made. The link's authority is precisely what makes this more dangerous than an un-cited claim — research finds LLM citations are fabricated/inaccurate at high rates even when they *look* authoritative ([PMC](https://pmc.ncbi.nlm.nih.gov/articles/PMC12658395/); [PMC – reference accuracy](https://pmc.ncbi.nlm.nih.gov/articles/PMC12829275/)).
2. **Animal-study-as-human-advice.** A mechanistic or rodent finding (which web search surfaces readily) is presented as actionable human guidance — graded `strong`/`grounded` instead of `animal-only` — and the user extrapolates a supplement, fasting, or macro change from evidence that has not been shown in humans ([nutrition evidence hierarchy](https://www.eufic.org/en/understanding-science/article/the-levels-of-evidence-in-nutrition-research)).
3. **A grounded link lending false authority to a weak claim ("citation-washing").** A single observational study or preprint gets a real, clickable source; the *presence* of the link nudges the perceived confidence upward, so a `weak`/`moderate`-grade finding reads as settled — the confidence label and the link-authority pulling in opposite directions ([limitations of observational evidence](https://pmc.ncbi.nlm.nih.gov/articles/PMC3884102/)).
4. **Grounded/un-grounded collapse → silent provenance loss.** A live-source-backed claim and an un-grounded training-knowledge "from research" claim render indistinguishably to a skimming reader, so the user can no longer tell which advice has a real source behind it — the exact distinction Phase 5's two-axis honesty exists to preserve (D-04; [Norwegian critical-health-literacy study](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC10995534/)).
5. **Recency mistaken for authority on fast-moving nutrition topics.** Because web search preferentially returns *fresh* results, a single new study is stated as if it overturns established consensus, without positioning it against the broader body of evidence ([single-study contextualization gap](https://pmc.ncbi.nlm.nih.gov/articles/PMC8479747/)).
6. **PII egress via the search query string.** The model folds the user's specific health details or note free-text into an outbound web-search query, leaking PII off-device (D-10) — a privacy failure unique to the web-enabled path.

### Regulatory / Compliance Context

State honestly what genuinely applies versus what does not, and why:

- **FDA medical-device / clinical software regulation — NOT applicable (by design).** The product is a general-wellness, single-user self-tracking app. It does not diagnose, treat, cure, or mitigate disease, and does not provide individualized clinical decision support for a patient under care. Under FDA's general-wellness policy, low-risk products intended to maintain/encourage a healthy lifestyle are generally not regulated as medical devices. **This is exactly why the "no clinical guardrails" decision is defensible** — but it also means the *only* thing standing in for a disclaimer is honest evidence grading + citation integrity, which is what the eval must protect.
- **FTC health-claims / substantiation framing — applies in spirit, not as a legal obligation here.** The FTC standard that health/efficacy claims be truthful and substantiated by competent and reliable scientific evidence is the right *north star* for what "good grounding" means, even though there is no advertising, no commerce, and no third party being marketed to (single user, local app). It is the principled basis for the evidence-quality-honesty rubric, not a compliance gate.
- **HIPAA — NOT applicable.** No covered entity, no business associate, no transmission of protected health information to a healthcare provider/payer. The user holds their own record on their own device. Do not invent HIPAA obligations for a local single-user personal record.
- **GDPR/CCPA data-subject obligations — NOT applicable in the usual sense.** The user is the sole data subject and the sole data controller of their own local data; there is no operator processing others' personal data. The one genuinely relevant *privacy* concern is engineering, not regulatory: the web-search query is the only path that egresses personal health detail off-device (D-10) — handled as a system-prompt + tool-arg-validation control, not a compliance requirement.

**Net:** No external regulatory gate binds this phase. The substantive constraints are *self-imposed and product-defining* — honest evidence grading, citation integrity, and keeping PII off the outbound query — which is precisely why they must be enforced through the eval rather than assumed.

## 2. Framework Decision

**Selected Framework:** `@anthropic-ai/sdk` — direct Anthropic TypeScript SDK (NO agent framework layered on) + the native `web_search_20250305` server tool.

**Version:** `@anthropic-ai/sdk ^0.92.0` (adopted Phase 3, sole importer `anthropic-api.service.ts`, D-17 transport boundary). Web-search tool version pinned to `web_search_20250305` (stable) per D-01. Angular 18.2, TypeScript 5.5 (strict).

**Rationale:**
Phase 5 is **net-zero new dependencies**. It registers exactly one Anthropic server-side tool (`web_search_20250305`) into the existing `tools[]` array on the Phase 4 `runAgenticLoop` and lets the loop render the resulting `server_tool_use` / `web_search_tool_result` turn inline — never routing it through `ToolRegistryService.dispatch` (D-02). The SDK already exposes typed shapes for `WebSearchTool20250305`, `WebSearchToolResultBlock`, and `web_search_result_location` citation blocks; the loop's `pause_turn` branch (Phase 4 D-16) was built specifically to absorb a server tool with no rework; and the `isLinkableCitation` allow-list + `parseClaimSpans` citation guard (Phase 4) extend to admit `web_search_result_location`. Adopting any agent framework would discard working Phase 3/4 plumbing for zero gain. This confirms and continues the Phase 4 AI-SPEC §2 framework decision.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| Claude Agent SDK (TypeScript) | Only other Anthropic-native TS option, but its Node-runtime code/filesystem/shell/MCP primitives are unusable in this browser/Electron-renderer sandbox; Phase 5 introduces no MCP requirement. |
| LangChain.js / LangGraph.js | Heavyweight agent-orchestration abstraction over a single-user app that already has a working bounded loop; discards Phase 3/4 plumbing; adds vendor-neutral indirection the locked Anthropic-native decision explicitly rejects. |
| RAG stack (vector DB + embeddings) | Locked project decision: "Anthropic-native tool use, not RAG/embeddings." Web grounding is a server-side search tool, not document retrieval; no corpus to index. |

**Vendor Lock-In Accepted:** Yes (Anthropic) — a conscious, pre-existing project decision. The `web_search` server tool deepens it (server-side execution is Anthropic-proprietary), but the D-17 transport boundary (`anthropic-api.service.ts` sole SDK importer; models/services stay SDK-type-free via local structural shapes) contains the blast radius if a future migration is ever needed.

### Entry Point Pattern
```typescript
// (A) services/anthropic-api.service.ts — the tool definition is built HERE and only here (D-17).
// Off by default; only appended to tools[] when the user has opted in via /settings (D-10 privacy posture).
import type { WebSearchTool20250305 } from '@anthropic-ai/sdk/resources/messages';

buildWebSearchTool(settings: AiToolSettingsSnapshot): WebSearchTool20250305 | null {
  if (!settings.enableWebSearch) return null;              // OFF by default — opt-in only (D-10)
  return {
    type: 'web_search_20250305',                          // STABLE version pinned (D-01)
    name: 'web_search',
    max_uses: settings.webSearchMaxUses ?? 3,             // D-06 cost cap — default 3, user-configurable + surfaced
    // allowed_domains / blocked_domains: param EXISTS but intentionally UNUSED this milestone (D-07).
    // user_location: omitted — localization would leak coarse location; not needed for research grounding.
  };
}

// In the request assembly, append it to the EXISTING Phase 4 tools[] (query_* + memory):
const tools = [
  ...this.clientToolDefs,                                  // Phase 4 query_* + memory (client tools)
  ...(webSearchTool ? [webSearchTool] : []),               // server tool — same array, different execution model
];

// (B) services/chat.service.ts — runAgenticLoop is UNCHANGED in shape. The web-search turn is
// rendered like any assistant turn; it is NEVER dispatched through ToolRegistryService (D-02).
// Two branches of the existing switch carry Phase 5:
//
//   case 'pause_turn':                 // long server-tool turn — RESUME by re-sending the paused
//     turn--;                          //   assistant turn UNMODIFIED; do NOT count it against maxAgentTurns
//     continue;                        //   (Phase 4 built this branch defensively; Phase 5 makes it live)
//
//   case 'tool_use':                   // CLIENT tool turn (query_*/memory) — dispatch as before
//     break;
//
// A turn whose content holds server_tool_use + web_search_tool_result but ends 'end_turn' needs NO
// special branch — it exits cleanly like any text turn. The ONLY new loop work is: do not treat a
// server_tool_use block as a client tool_use to dispatch.

const serverToolBlocks = response.content.filter(
  (b): b is ServerToolUseBlock => b.type === 'server_tool_use',
);
const webResultBlocks = response.content.filter(
  (b): b is WebSearchToolResultBlock => b.type === 'web_search_tool_result',
);
// Emit live UI feedback (D-05) — NO dispatch, NO tool_result posted back (Anthropic already ran it):
for (const stu of serverToolBlocks) {
  subscriber.next({ kind: 'web_search_started', query: (stu.input as { query?: string }).query ?? '' });
}
for (const wr of webResultBlocks) {
  // content is WebSearchToolResultError | WebSearchResultBlock[]
  if (Array.isArray(wr.content)) {
    subscriber.next({ kind: 'web_search_results', count: wr.content.length });   // "✓ Found N sources" (D-05)
  } else {
    subscriber.next({ kind: 'web_search_error', code: wr.content.error_code });  // surface honestly, do not retry
  }
}
// IMPORTANT: do NOT push a ToolResultBlockParam for a server tool, and do NOT add 'web_search' to
// WRITE_PROPOSAL_TOOLS — isWriteProposal stays false (read-only, like query_*). The assistant turn
// (text + server_tool_use + web_search_tool_result + cited text) is pushed back as-is for the next turn.
```

> **Why no `tool_result` round-trip:** per Anthropic's server-tools docs — *"Unlike client `tool_use` blocks, you don't need to respond with a `tool_result`. The result block appears immediately after the `server_tool_use` block in the same assistant turn."* The client's only jobs are: (1) render it, (2) honor `pause_turn`, (3) push the assistant content back unmodified so the encrypted citation indices survive the next turn.

### Common Pitfalls
<!-- Verified against the live Anthropic web-search + server-tools docs (2026-05-31) and the 0.92.0 type defs. -->

1. **Dispatching `server_tool_use` through `ToolRegistryService` → double-bill + wedge (D-02, highest-stakes loop bug).** It is named `web_search` like a client tool, but Anthropic already ran it and already returned `web_search_tool_result` in the same turn. If the loop treats it as a client `tool_use`, it tries to execute a tool that has no executor (throws or returns a junk `tool_result`), confusing the next turn. **Mitigation:** the loop filters `b.type === 'server_tool_use'` for render-only; `ToolRegistryService.dispatch` is reached only by `b.type === 'tool_use'`; `'web_search'` is NEVER added to `WRITE_PROPOSAL_TOOLS` or the dispatch table. A `chat.service.spec.ts` case asserts a server-tool turn produces zero `dispatch` calls.

2. **A `pause_turn` web-search turn counted against `maxAgentTurns`, or its content mutated before resume.** Anthropic's guidance is explicit: re-send the conversation **including the paused assistant response, unmodified**, with the same tools. Decrementing/rebuilding the turn, or dropping the `server_tool_use`/`web_search_result` blocks, breaks the resume and can re-bill the search. **Mitigation:** the existing `case 'pause_turn': turn--; continue;` branch pushes the assistant block exactly as received; the serializer preserves server-tool blocks verbatim (incl. `encrypted_content`). Defensive in Phase 4 — load-bearing now.

3. **Free-text the model wrote (`Smith et al. 2019`, a bare DOI/URL) rendered as a clickable link even with web search ON (D-09, the headline failure mode — research Pitfall 1, 14–95% fabrication).** Web search now *does* produce real links, which makes it tempting to relax the guard — exactly backwards. The model can still write a citation-shaped string in prose that has NO backing `web_search_result_location`. **Mitigation:** ONLY a `CitationsWebSearchResultLocation` block (narrowed + `https:`-gated at the D-17 chokepoint) becomes `<a href>`; prose stays inert plain text via the strict markdown subset (`bypassSecurityTrust*` forbidden). The Phase 4 adversarial test extends to the full matrix: web-search OFF → "find a study about X" yields zero links; web-search ON → only structured blocks link, free-text prose stays plain.

4. **Grounded vs un-grounded "from research" collapsed into one rendering (D-04).** A live-source-backed claim (`from research · grounded`, with a footnote link) must be visibly distinct from an un-grounded training-knowledge "from research" claim (plain text, no link, Phase 4 framing). If both render identically the two-axis honesty is silently lost. **Mitigation:** the source axis upgrades to `grounded` ONLY when a `web_search_result_location` actually backs the claim; otherwise it stays the Phase 4 un-grounded plain-text framing. Color is never the only channel (CLAUDE.md a11y). Adversarially tested both ways (D-09).

5. **PII/health specifics or per-entry free-text notes leaking into the search QUERY string (D-10, privacy).** With web search ON, the model formulates `web_search` query strings that **egress the device** — the one place the app's local-only posture is widened. A query like "is keto safe for someone with [user's specific condition from their notes]" sends PII to the web. **Mitigation:** a system-prompt instruction discourages embedding the user's personal/health specifics or per-entry free-text notes into query strings (general research phrasing only); `validators.ts` re-validation of model-proposed tool args stays binding (CHAT-11); web search is OFF by default so the surface only exists on deliberate opt-in.

6. **Web-search errors mishandled because the API returns HTTP 200.** A rate-limit / `max_uses_exceeded` / `query_too_long` is NOT a transport error — it arrives as `content: { type:'web_search_tool_result_error', error_code }` inside a 200 response. Treating the turn as a hard failure (or assuming `content` is always an array) crashes the render. **Mitigation:** always narrow `WebSearchToolResultBlock.content` against the `WebSearchToolResultError` union; on error, surface an honest "couldn't reach the web" row (D-05) and let the model finish from its own knowledge — never retry blindly (re-billing risk). Errored searches are not billed.

7. **Server-tool blocks stripped/reordered by the serializer → broken later-turn citations.** `encrypted_content` (on `web_search_result`) and `encrypted_index` (on the citation) must round-trip unmodified for multi-turn citation resolution. The Phase 3/4 `chat-block-serializer` was built for client `tool_use`/`tool_result`; it must now also pass `server_tool_use` / `web_search_tool_result` through verbatim. **Mitigation:** serializer preserves server-tool blocks as-is on replay; a spec asserts a round-trip of a web-search turn is byte-stable for the encrypted fields.

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns adapted to THIS TypeScript/Angular project + the opt-in web-search server tool — not generic. Extends Phase 4's §4b (read it for the loop-wide async/prompt/cost posture); this section covers what web search adds.

### Structured Outputs & Runtime Validation (TypeScript — no Pydantic)

This is a TypeScript-strict project with **no Pydantic** and (per CONVENTIONS) no `zod`/`instructor` runtime layer in the hot path. The project's equivalent of "schema-validated model output" is the **pure, DI-free runtime-validation module** pattern already established by `validators.ts`, `chat-block-serializer.ts`, and the Phase 4 `parseClaimSpans` allow-list parser. Web search adds **two** surfaces that need it.

**(a) Narrowing + gating web citations at the D-17 chokepoint.** The SDK hands back a `TextCitation` union on `TextBlock.citations`. Before anything reaches the renderer, a pure module narrows the union to the one allowed citation type, drops anything not `https:`, and converts to a **local SDK-free shape** — so SDK types never leak past the transport boundary (D-17) and the renderer can never be tricked into linking a non-structured string (D-03/D-09):

```typescript
// services/web-citation-parser.ts — PURE module, no Angular DI (mirrors validators.ts / parseClaimSpans).
// Input: SDK citation objects (only at the transport boundary). Output: local, SDK-free GroundedCitation[].
import type { TextCitation } from '@anthropic-ai/sdk/resources/messages';

/** Local structural shape — what the renderer sees. NO SDK types past this point (D-17). */
export interface GroundedCitation {
  readonly url: string;        // GUARANTEED https: (gated below)
  readonly title: string;      // falls back to the host when the API title is null
  readonly citedText: string;  // the cited_text excerpt (≤150 chars), for the footnote tooltip
}

/** Total function — any input returns a valid GroundedCitation[]; never throws, never fabricates a link. */
export function toGroundedCitations(citations: readonly TextCitation[] | undefined): GroundedCitation[] {
  if (!citations) return [];
  const out: GroundedCitation[] = [];
  for (const c of citations) {
    // (1) ALLOW-LIST: only the structured web-search citation may become a link (D-09).
    if (c.type !== 'web_search_result_location') continue;        // ignore every other citation type
    // (2) HTTPS GATE: a non-https url is dropped entirely — never rendered as a link (D-03).
    let parsed: URL;
    try { parsed = new URL(c.url); } catch { continue; }          // unparseable ⇒ drop, no throw
    if (parsed.protocol !== 'https:') continue;                   // http:/ftp:/javascript: ⇒ dropped
    out.push({
      url: parsed.toString(),
      title: c.title?.trim() || parsed.host,                      // null title ⇒ show the host, never blank
      citedText: c.cited_text ?? '',
    });
  }
  return out;
}

/** Dedupe by URL for the per-message "Sources" list (the model often cites one source twice). */
export function toSourcesList(citations: readonly GroundedCitation[]): GroundedCitation[] {
  const seen = new Set<string>();
  return citations.filter((c) => (seen.has(c.url) ? false : (seen.add(c.url), true)));
}
```

- **How the SDK integrates:** `anthropic-api.service.ts` (the sole SDK importer) calls `toGroundedCitations(textBlock.citations)` while mapping each assistant turn into the local `ChatBlock` shape. The renderer's `isLinkableCitation` allow-list (Phase 4) now consumes `GroundedCitation[]` — and **only** that — to emit the inline footnote `[n]` + Sources list. There is no path from a prose string to an `<a href>`.
- **Why not forced JSON / `tool_choice` structured output:** citations are first-class API objects already; re-asking the model for a JSON envelope would (a) reintroduce the fabrication risk the structured blocks eliminate and (b) fight streaming. The narrow-and-gate-the-real-blocks approach is strictly safer.
- **Retry logic:** **none.** A web-search error (`max_uses_exceeded`, `too_many_requests`, …) arrives in a 200 response; the loop surfaces an honest "couldn't reach the web" row (D-05) and lets the model finish from its own knowledge — it does **not** re-call (re-billing + still no guarantee). A malformed/non-https citation is silently dropped (degrades to an unbadged, unlinked claim — D-09). Nothing is logged to the API; nothing beyond the inert claim surfaces to the user.

**(b) Tool-arg re-validation still binds (CHAT-11 / D-10).** The web-search tool's only model-authored input is the **query string**, which is server-executed and egresses the device. `validators.ts` re-validation of model-proposed tool args stays binding for the client `query_*`/`memory` tools; for web search, the privacy control is the **system-prompt instruction** discouraging PII/health-specifics/free-text-notes in query strings (D-10) plus the opt-in default (OFF). The query is not silently rewritten — but it is bounded by an explicit, surfaced posture.

### Async-First Design

- **How async works here:** unchanged — the SDK returns Promises; the loop wraps the whole multi-turn sequence in one `new Observable(...)` running an `async` IIFE, emitting `ChatTurnEvent`s. A web-search turn is **still one awaited `messages.create`** — Anthropic runs the search server-side inside that single call, so there is no extra Promise to juggle. A `pause_turn` simply means the loop awaits **another** `messages.create` (the resume) before the turn completes.
- **The one common mistake:** treating a `pause_turn` as a terminal state and `subscriber.complete()`-ing the Observable — the turn isn't done, the model paused mid-search. Equally: forgetting `takeUntilDestroyed(this.destroyRef)`, so navigating away during a long web-search turn leaves the loop awaiting (and billing) a continuation. **Mitigation:** `pause_turn` does `turn--; continue;` (never `complete`); the Observable teardown sets `cancelled = true`, checked each iteration.
- **Stream vs. await:** **await** the full `Message` per turn (Phase 4 stance) so `toGroundedCitations` sees the complete `citations` array and the footnote numbering is stable. The live "🔎 Searching the web…" → "✓ Found N sources" feel (D-05) comes from `ChatTurnEvent`s emitted between awaited turns, not from token streaming. (The SDK does stream `server_tool_use`/`web_search_tool_result` SSE events if ever needed, but per-turn await keeps citation parsing simple — token streaming stays deferred.)

### Prompt Engineering Discipline

- **System vs. user separation:** the web-search additions live entirely in the **cached system prompt** (built by `FitnessContextService`): (1) **when to search** (D-08) — "prefer the user's own logged data and your training knowledge; reach for `web_search` for genuinely current or research-grounded questions — recent studies, current guidelines — not for questions you can answer from training knowledge or the user's data"; (2) **grounded-vs-un-grounded framing** (D-04) — "when a claim is backed by a live web source, it will carry a citation; an un-grounded 'from research' claim is your training knowledge — label it as such and do not present it as a live source"; (3) **the query-string privacy rule** (D-10) — "do NOT put the user's personal or health specifics, or their per-entry free-text notes, into web-search query strings; phrase searches in general terms (the query leaves the device)." User turns carry only the user's message; untrusted user strings stay inside the CHAT-11 `<user_*>` delimiters.
- **Few-shot:** keep 1–2 short inline exemplars in the cached prefix — one showing a general, PII-free research query ("recent guidelines on resistance training frequency" — not "training plan for [the user's condition]"), one showing a grounded vs un-grounded research claim. Do **not** dynamically retrieve examples (no retrieval layer; it would churn the cache).
- **Token budget:** `max_tokens` always explicit (`4096`). The web-search tool definition adds a small, stable tool-schema cost to the cached prefix; the variable cost is the `web_search_result` content counted as input tokens across the searching turn and subsequent turns (budget for it in the rolling-window check).

### Context Window Management

System type is the bounded agentic loop (Conversational) — conversation summarization + per-turn retrieval, not RAG chunking. Web search adds one wrinkle:
- **Web results inflate the window across turns:** `web_search_result` content is counted as input tokens in the searching turn **and** in subsequent turns (it rides along for citation resolution). `messages.countTokens` (not `text.length/4`) drives the summarize decision every send; summarize older turns when the budget is crossed, while keeping the cached prefix byte-stable (Phase 4 Pitfall 4).
- **`max_uses` is a window control too (D-06):** capping searches per turn (default 3) caps how much fetched web content enters the window in one turn.
- **Cap, not crash:** `maxAgentTurns` still bounds the loop; a `pause_turn` resume does **not** consume a turn (so a long search can't exhaust the cap by pausing). Hitting the cap surfaces the honest best-effort notice (Phase 4 D-04).
- **Serializer preserves encrypted fields:** dropping `web_search_result` blocks to "save tokens" breaks multi-turn citations — summarize *older chat turns*, never the encrypted server-tool blocks of a turn whose citations are still live.

### Cost and Latency Budget

- **Per-turn cost (Sonnet 4.6, $3/M in · $15/M out) + search surcharge:** web search is billed **$10 per 1,000 searches** ($0.01 each) **on top of** token cost. With `webSearchMaxUses = 3` (D-06), a turn that searches costs **≤ 3¢ in search fees** plus tokens. The fetched `web_search_result` content (counted as input tokens) is the larger variable — a research answer drawing several sources can add a few thousand input tokens that also persist into later turns. Rough envelope for a web-grounded answer: **~3–8¢** (search fees + inflated input + ~500–1,500 output tokens), versus the ~1–3¢ Phase 4 non-search answer. `max_uses` is the hard ceiling on the search-fee portion; `maxAgentTurns` bounds the loop.
- **Latency:** a searching turn is slower (server-side search + fetch + synthesis) and may emit `pause_turn` for long searches — hence the live "🔎 Searching the web…" feedback (D-05) so the user isn't staring at a dead spinner.
- **Caching:** `cache_control: ephemeral` on the stable system prefix (incl. the web-search tool definition, which accepts `cache_control`) keeps repeat-turn system cost at 0.1×. The dynamic `web_search_result` blocks are never cached. Errored searches are not billed — so a `max_uses_exceeded` or rate-limit costs nothing in search fees.
- **Cheaper-model routing (4b.5):** keep the web-search loop on **Sonnet 4.6** — deciding *when* to search and how to grade a live source is exactly where model quality pays off; routing it to Haiku would degrade both. Reserve `claude-haiku-4-5` ($1/M in) for the rolling-window **summarization** sub-task only (Phase 4 stance).
- **Semantic caching:** not applicable (single-user, bursty chat — no cross-user overlap). Exact-match prompt caching of the stable prefix is the relevant mechanism. The default OFF posture (D-10) is itself a cost control: zero search fees until the user opts in.

## 5. Evaluation Strategy

> **Stack reality (binding):** This is an Angular 18 + TypeScript 5.5 (strict) browser/Electron app tested with **Jasmine + Karma + axe-core** (`ng test --no-watch`). There is **no Python, no RAGAS, no pytest, no LLM-judge harness in CI**. The primary eval mechanism is **deterministic, code-based Jasmine specs run over hand-built fixtures** (the existing codebase pattern: canned Anthropic responses + jasmine spies on the SDK transport — see `chat.service.spec.ts`, `confidence-attribution-parser.spec.ts`, `chat-message-list.component.spec.ts`). The subjective evidence-honesty dimensions are evaluated by a **lightweight offline spot-check** the single developer/owner runs — not a CI judge. This section maps each Section 1b rubric ingredient to a measurement approach that is real for this stack.

### Dimensions

Each dimension below traces to a Section 1b rubric ingredient (the practitioner-language Good/Bad) and a Phase 5 decision (D-0x). "Measurement" is the *realistic* mechanism for this stack.

| # | Dimension (← §1b ingredient) | Rubric (PASS / FAIL in domain language) | Measurement | Priority |
|---|------------------------------|------------------------------------------|-------------|----------|
| **E1** | **Citation-link integrity** ← "no fabricated links" (CFM-1, D-09, research Pitfall 1) | **PASS:** Across the OFF/ON matrix, the rendered message contains an `<a href>` **only** where a structured `web_search_result_location` block backs the text, and every such href is `https:`. A "find a study about X / give me the DOI" prompt with web search **OFF** yields `querySelectorAll('a').length === 0`; with web search **ON**, only structured-block-backed footnotes are anchors and any author-year / DOI / bare-URL string the model wrote *in prose* renders as inert plain text. **FAIL:** any `<a>` traces to a free-text prose string, or a non-`https:` URL becomes clickable, or `toGroundedCitations` ever emits a link from a non-`web_search_result_location` citation. | **Code** — deterministic Jasmine spec. THE single most important eval artifact (the adversarial citation regression test, RESCH-03/D-09). Extends Phase 4's `isLinkableCitation` guard test; asserts on `querySelectorAll('a')` against canned-response fixtures + on `toGroundedCitations()` / `toSourcesList()` unit cases (allow-list + https gate + null-title host fallback). Hard pass/fail; **zero tolerance**. | **Critical** |
| **E2** | **Grounded vs un-grounded distinguishability** ← "can a skimming reader tell?" | **E4** | **Web-search error resilience** ← HTTP-200 error union (Pitfall 6, D-05) | **PASS:** a `web_search_tool_result` whose `content` is a `web_search_tool_result_error` (`max_uses_exceeded` / `too_many_requests` / `query_too_long` / `unavailable` / `invalid_tool_input` / `request_too_large`) renders an honest "couldn't reach the web" row, the model finishes from its own knowledge, and **no** retry/re-call is issued. **FAIL:** the error union is treated as an array (render crash), the turn is treated as a hard transport failure, or the loop blindly re-calls (re-bill). | **Code** — Jasmine spec over an error-shaped fixture for each `WebSearchToolResultErrorCode`; asserts no throw, an error `ChatTurnEvent`, and zero re-call. | **High** |
| **E5** | **PII containment in outbound query** ← "does the search leak PII?" (CFM-3, D-10, CHAT-11) | **PASS:** the system prompt instructs general, PII-free query phrasing; web search is OFF by default; the model's per-entry free-text notes / specific vitals values are not folded into a query string; `validators.ts` re-validation of client tool args stays binding. A negative-case fixture (a prompt baiting the model to search "for someone with [user's condition]") is reviewed in the owner spot-check for whether the emitted query stayed general. **FAIL:** the system prompt omits the privacy instruction; a query string in a captured trace contains a user note's free text or a specific vitals value. | **Code** (prompt-presence assertion: a `fitness-context.service.spec.ts` case asserts the system prompt contains the D-10 query-privacy instruction + OFF-by-default wiring) **+ Human spot-check** (owner reviews actual emitted query strings on real searches — there is no deterministic way to prove the *model's* phrasing without a judge). | **High** |
| **E6** | **`webSearchMaxUses` cost-cap binding & visibility** ← unbounded-cost failure (CFM-5, D-06) | **PASS:** `buildWebSearchTool` sets `max_uses` to the configured `webSearchMaxUses` (default 3) on the request, and the configured value is rendered near the toggle in `/settings/ai`. **FAIL:** `max_uses` is unset/hardcoded away from the setting, or the cap is not surfaced to the user. | **Code** — unit spec on `buildWebSearchTool(settings)` asserting `max_uses === settings.webSearchMaxUses`; component spec asserting the cap value is in the settings DOM. | **High** |
| **E7** | **Citation–claim support match** ← "does the linked source actually say this?" (§1b Critical, Pitfall 1/3) | **PASS (judged):** every grounded `[n]` points to a source whose `cited_text` genuinely supports the specific sentence it is attached to; the claim does not over-state the source. **FAIL:** a footnote is attached to a sentence the source does not support — an authoritative-looking link laundering an unsupported claim (citation-claim mismatch). | **Human spot-check** (owner / EBM-literate calibrator). Honestly **not** automatable on this stack — it requires reading the linked source against the sentence. This is the realistic flywheel for a single-user app, not a CI gate. Optional future: an offline LLM-judge pass (Claude grading its own `cited_text` ↔ sentence support) run **manually by the owner**, calibrated against the spot-check — never wired into `ng test`. | **Critical** (of the judged dimensions) |
| **E8** | **Evidence-quality honesty** ← "is the grading faithful to the study design?" (§1b High) | **PASS (judged):** the confidence label matches the study design — single observational/cohort → `weak`/`moderate`; `strong` reserved for systematic reviews / meta-analyses / convergent RCTs; mechanistic/rodent → `animal-only`; the label does **not** drift upward merely because a live link now exists ("citation-washing"). **FAIL:** observational-as-settled, animal-as-human, or confidence inflated by link presence. | **Human spot-check** (owner, calibrated by RD / exercise-physiologist standards encoded in the rubric). Subjective + domain-bound; offline, not CI. | **High** (of the judged dimensions) |
| **E9** | **No overstatement of preliminary / single-source findings** ← "recency ≠ authority" (§1b High) | **PASS (judged):** a recent/single/preliminary finding is framed as emerging ("one recent study suggests…") and positioned against the broader body of evidence; a newer weak source does not override established consensus. **FAIL:** a single fresh study (which web search surfaces well) stated as if it settles/overturns the question; "from research" used as a uniform stamp. | **Human spot-check** (owner). Offline flywheel signal, not CI. | **Medium** |

> **Why E1–E6 are Code and E7–E9 are Human:** E1–E6 are *structural/behavioral* properties of the rendering and the loop — fully decidable from the DOM and the SDK response shape, so they are deterministic Jasmine assertions and belong in CI. E7–E9 are *judgments about meaning* (does this source support this sentence? is this grade honest?) — not decidable from structure, requiring a human (or a calibrated judge run by hand). Conflating the two would either (a) fake-test the subjective ones with brittle string matches or (b) leave the structural ones to slow human review. The split is deliberate.

## 6. Guardrails

> For a single-user, privacy-first local app, "online guardrails" are the **real-time client-side gates already in the architecture** — they run in-process on every web-enabled message, add no network hop, and block the catastrophic failures (fabricated link, PII egress, runaway cost). The "offline flywheel" is the **owner's signal-driven spot-check** of grounded answers for the judged dimensions (E7–E9) — the realistic improvement loop when there is one user and one reviewer.

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| **Structured-only + https-only citation-link gate** (`toGroundedCitations`, D-03/D-09) | Every assistant turn rendered, web search ON or OFF | **Block.** Only a `web_search_result_location` whose url parses as `https:` becomes an `<a href>`; every other citation type and every non-https url is silently dropped (degrades to an inert, unlinked claim). The renderer has **no** prose-string→link path (`bypassSecurityTrust*` forbidden, strict markdown subset). This is the E1 invariant enforced at runtime, not just in test. |
| **`webSearchMaxUses` cost cap** (D-06) | Every web-enabled request assembly | **Bound/Block.** `max_uses` (default 3) is wired to the request so Anthropic stops searching at the ceiling; `max_uses_exceeded` returns an inert error row (handled, not retried). The configured value is surfaced near the toggle so the ceiling is visible. |
| **Tool-arg re-validation** (`validators.ts`, CHAT-11) | Every **client** `query_*` / `memory` tool call | **Block.** Model-proposed client tool args are re-validated against `validators.ts` before execution; invalid args throw rather than persist or query. (The server-side `web_search` query is not client-dispatched, so the binding control for *it* is the system-prompt PII rule below + OFF-by-default.) |
| **System-prompt PII-query discouragement + OFF-by-default + per-note redaction** (D-10) | Web search enabled by deliberate opt-in | **Flag/Bound.** Web search is OFF by default (the surface does not exist until opt-in); the cached system prompt instructs general, PII-free query phrasing and not embedding per-entry free-text notes or specific vitals into queries; the per-entry note redaction toggle operates at free-text-note granularity. (Best-effort behavioral guard — the model authors the query, so this bounds rather than hard-blocks; reinforced by the E5 spot-check.) |
| **Server-tool no-dispatch / no-`tool_result` gate** (D-02) | Any turn containing `server_tool_use` | **Block.** `server_tool_use` is render-only; it is never routed to `ToolRegistryService.dispatch`, never added to `WRITE_PROPOSAL_TOOLS`, and no `tool_result` is posted back — preventing the double-bill/wedge (E3). `pause_turn` resumes unmodified without consuming a turn. |

### Offline (Flywheel)

| Metric | Sampling Strategy | Action on Degradation |
|--------|------------------|----------------------|
| **Citation–claim support-match rate (E7)** | Owner spot-checks grounded answers, weighted toward signal: any answer the owner *acted on* (changed diet/training), any answer with ≥2 sources, any answer on a fast-moving nutrition topic. Read each `[n]`'s `cited_text` against the sentence it backs. | If mismatches recur → tighten the D-08 system-prompt grounding instruction (require the claim not exceed the source) and add the mismatching shape as a new fixture; consider the optional manual LLM self-judge pass. |
| **Evidence-grade honesty rate (E8)** | Same sampled grounded answers; check the confidence label against the study design behind the source (observational vs RCT vs meta-analysis vs animal). | Recurring inflation → strengthen the evidence-hierarchy instruction in the system prompt; flag "label drifted up because a link exists" (citation-washing) explicitly. |
| **Preliminary-finding overstatement rate (E9)** | Weight toward answers citing a single recent study / preprint (the kind web search surfaces). | Recurring overstatement → add "position single findings against the broader body of evidence; recency is not authority" emphasis to the prompt. |
| **PII-in-query incidents (E5)** | Review emitted query strings on real searches (dev console / instrumentation log, local only). | Any incident → harden the D-10 prompt rule and re-examine whether the note-redaction default should change. |

## 7. Production Monitoring

> **Honest reconciliation of the GSD Arize-Phoenix default vs. this app's privacy posture.** The GSD default tracer is Arize Phoenix. This is a **single-user, privacy-first, local browser/Electron app** whose entire core value is *"nothing leaves the machine except the user-initiated Anthropic request."* Shipping a cloud/SaaS tracer would directly **contradict** that posture by opening a second egress channel for chat content and health context — exactly what the app exists to prevent. **Decision: decline an external/cloud tracer for production.** Production "monitoring" for a single-user local app realistically means **in-app deterministic instrumentation** — the cost/usage counters, the visible `webSearchMaxUses` cap, the live in-stream search-feedback rows (D-05), and structured dev-console logs that never leave the device. Arize Phoenix is acceptable **only** in its fully self-hosted/local mode (`localhost:6006`, no data egress) and **only** for optional dev-time eval-trace inspection by the owner — never as a default-on production dependency. This override is intentional and documented per the project's privacy invariant; do not stamp a cloud tracer onto this app.

**Tracing Tool:** **In-app local instrumentation (primary).** Structured, local-only console/log events emitted by `chat.service.ts` / `anthropic-api.service.ts` for each web-enabled turn (search count, cap, result count, error code, grounded-citation count, fabricated-link count). The user-facing `ChatTurnEvent` rows (`web_search_started` / `web_search_results` / `web_search_error`, D-05) are the live in-product trace. **Arize Phoenix — optional, local self-hosted only**, for the owner's dev-time eval runs; declined for production on privacy grounds (above).

**Key Metrics to Track** (all computed locally, nothing transmitted):
1. **Fabricated-link count** — number of `<a href>` not backed by a structured `web_search_result_location`. **Must be 0** at all times (the E1 invariant). In test this is the adversarial assertion; in-app it is logged for defense-in-depth.
2. **Web searches per message vs. cap** — actual `server_tool_use` count per turn against `webSearchMaxUses` (3). Surfaces cost behavior and whether the cap binds.
3. **Grounded-vs-un-grounded claim ratio** — count of `grounded` (linked) "from research" claims vs un-grounded ones per answer. The provenance health signal behind E2.
4. **Web-search error rate** — share of `web_search_tool_result` turns returning the error union (`max_uses_exceeded` / `too_many_requests` / `unavailable` / …), so a degraded search path is visible (errored searches are unbilled but signal trouble).
5. **Cost per web-grounded answer** — search fees (`$0.01 × searches`, ≤3¢ at cap) + token cost (the `web_search_result` content rides along as input tokens across turns). Surfaced from the existing token instrumentation so the user sees the price of grounding.

**Alert Thresholds** (single-user → "alert" = a failing test or an in-app banner, not a pager):
- **ANY fabricated/non-https link in a test run = hard CI failure** (zero tolerance — the E1 red is the alert).
- **Web-search error rate elevated across a session** → the honest "couldn't reach the web" row already informs the user per occurrence; a sustained pattern is an owner-investigate signal (and a candidate new fixture).
- **Searches-per-message hitting the cap repeatedly** → surface that the `webSearchMaxUses` ceiling is being hit (cost-awareness), prompting the user to raise/lower it deliberately.
- **Quota / cost drift** is bounded structurally by `max_uses` + `maxAgentTurns` + the OFF-by-default posture — there is no unbounded runaway to page on.

**Smart Sampling Strategy** (signal-based selection for the owner spot-check, since exhaustive review of one user's chat is neither needed nor scalable): weight review toward interactions with concerning signals —
- answers the owner **acted on** (a real diet/training change) — highest stakes;
- answers with **≥2 grounded sources** or a **single fresh study / preprint** (citation-mismatch and recency-overstatement risk, E7/E9);
- answers on **fast-moving nutrition/exercise topics** where recency competes with consensus;
- any turn that **emitted a web-search error** or **hit the `max_uses` cap**;
- any turn whose emitted **query string looked specific** (E5 PII signal).
These are exactly the "retries / unusual length / explicit escalation" smart-sampling signals from `ai-evals.md`, translated to this domain. Everything reviewed feeds back as a new canned fixture (E1–E6) or a sharpened system-prompt instruction (E7–E9) — the flywheel.
