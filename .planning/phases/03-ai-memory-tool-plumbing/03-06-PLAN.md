**Gap closure: UAT Test 2 (Phase 3 SC3, severity: major).**

Fix the dev-seed pending-pill lifecycle bug diagnosed in `.planning/debug/dev-seed-pending-pill-not-rendering.md`. Today, clicking "Seed pending memory proposal" on `/settings/ai` and navigating to `/chat` silently consumes the sentinel from localStorage but never renders a pill, because `consumeDevSeedIfPresent()` runs in `ngOnInit` while `activeConversationId` is still `null` (it's only assigned on user click in `onSelectConversation` / `onNewChat`). The early-return guard at `chat-page.component.ts:233` fires AFTER `StorageService.consumeDevSeed()` has read-and-removed the sentinel — net effect: the seed is destroyed without being acted upon.

**Fix approach (chosen from the diagnosis options):**

Primary fix — **defer consumption until a conversation exists** (option #1 from the diagnosis). On `ngOnInit` after `loadConversations()` resolves: if conversations exist, auto-select the most-recent one. If none exist, auto-create one (mirroring `onNewChat`). Only THEN call `consumeDevSeedIfPresent()`. This matches user intent: a "seeded" pending memory should land on the user's most recent chat the next time they open /chat, regardless of whether they clicked anything in the sidebar.

This is the **minimum viable fix** — it does not touch `StorageService.consumeDevSeed()` (which can stay read-and-remove). The lifecycle ordering in `chat-page` is the only thing that needs to change, plus a regression spec that drives `ngOnInit` end-to-end (not `consumeDevSeedIfPresent` directly).

**Out of scope (deliberate):**

- No change to `StorageService.consumeDevSeed()` (option #2 was a fallback if the chat-page lifecycle fix were not feasible — it is).
- No new methods on `ChatService`.
- No UI changes to the pending pill itself or the message list — Plan 03-05's chat-message-list / pending-pill components are correct; only the consumer's init order is wrong.
- No fix for the other Anti-Patterns flagged in `03-VERIFICATION.md` (e.g., the `chat-page.component.ts:388–427` activeConversationId race in `onSendMessage`) — those are Phase 4/5 concerns and are out of this gap closure.

        .pipe(takeUntilDestroyed(this.destroyRef))

          // Capture the seed first so we can decide whether to auto-create.
